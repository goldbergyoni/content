Rule: One global process.on('unhandledRejection') handler

Register one process-wide handler for unhandled promise rejections so failures are observed and never crash the process silently.

An unhandled promise rejection leaves your application in an undefined, partially-failed state — a database write may be half-done, a request left hanging.

Without a process-level handler, recent Node.js versions terminate the process, so a single forgotten .catch() can take the whole service down with no log line explaining why.

Mandatory in every type of component — APIs, workers, CLIs, serverless functions and scripts. There is no architecture where an unobserved rejection is acceptable, so this rule carries no exceptions.

Register a single global unhandledRejection handler. Make the error observable — log it with full context through your logger — then crash or stay alive according to your chosen process strategy.

GOODserver.js
// somewhere a promise rejects without a local catch
Promise.reject(new Error('DB connection lost'));

// one global handler, registered once at startup
process.on('unhandledRejection', (reason) => {
  logger.error('Unhandled rejection', { reason });
  // decide here: crash or stay alive based on your strategy
});
BADserver.js
// a promise rejects...
Promise.reject(new Error('DB connection lost'));

// No handling — the process may crash silently

A rejected promise with no handler is the asynchronous equivalent of an uncaught exception. Catching it in one place lets you log the failure with full context and then make a deliberate decision about whether the process can safely continue. Adapted from the Node.js Best Practices guide.
