Testing Infra Review

New test suite under tests/ in compliance-ai-service — citations, workspace artifacts, and the Tartlet mock layer · June 10, 2026
⚠️ Warning: shallow review — based on one single talk and no code read. Treat the findings as discussion starters, not verified conclusions.

Overview

The new infra covers three areas: citation processing tests (tests/citations/, 3 files / ~330 lines), a workspace-artifacts validation test, and a 311-line recorded-response HTTP mock router (tests/tartlet_mock/tenant_responses.py) backed by dozens of recorded JSON fixtures per tenant. Nine findings below — expand "More info" on each for the details, code references, and the reasoning, drawn from the Node.js Testing Best Practices guide.

1. A mock data access layer is used instead of a real database

Important
More info

Where: tests/tartlet_mock/tenant_responses.py + recorded fixtures under tests/tartlet_mock/tenants/<tenant_id>/

The suite replays recorded Tartlet HTTP responses through a respx router instead of exercising a real data layer. The mock itself is substantial — 311 lines of routing logic with static entries, batch-endpoint callbacks, and path-filtered callbacks — plus a large tree of recorded JSON files that must be kept in sync via scripts/record_tartlet_responses.py. Every recording miss requires a manual re-record, and the mock's own filtering/lookup logic is now complex enough to harbor bugs of its own.

Why this matters

The best-practices guide ("Database and Infrastructure Setup") recommends testing against the real database/service technology, optimized for testing (e.g. spun up with testcontainers or docker-compose), rather than mocks or in-memory substitutes:

  • Mocks bypass production behavior. "Using it only for testing will bypass issues that exist in the production technique" — schema mismatches, query-layer bugs, pagination, error semantics and contract drift are all invisible when responses are pre-recorded.
  • Recorded fixtures rot. When the upstream API changes shape, the tests keep passing against stale recordings — the suite gives green confidence about a contract that no longer exists.
  • The mock becomes a second system to maintain. Batch-lookup callbacks, volatile-param stripping, and 5xx skipping (all present here) are production-grade logic living inside test infra, with no tests of their own.

Source: nodejs-testing-best-practices, Section 2 — Database and Infrastructure Setup.

2. Reliance on custom assertion logic instead of native pytest assertions

More info

Where: e.g. tests/citations/test_clean_citation_text.py:96-104, tests/citations/test_consecutive_ordering.py:132-139

Several tests build their own assertion machinery — hand-rolled scanning loops, compound boolean expressions, and custom failure messages — instead of plain, flexible pytest assertions that can be mixed and matched per case. Example:

lines = cleaned.split("\n")
for idx, line in enumerate(lines):
    if line.strip().startswith("question:"):
        preceding_non_empty = next((lines[j] for j in range(idx - 1, -1, -1) if lines[j].strip()), "")
        assert not set(preceding_non_empty.strip()) <= {"-", "=", "*", "_"} \
            or len(preceding_non_empty.strip()) < 3, f"Found setext underline before paragraph: ..."

When this fails, the reader must reverse-engineer the assertion logic before they can even understand what broke. A direct equality assertion against the expected cleaned string would fail with a clear diff.

Why this matters

The guide ("Component tests / test anatomy") recommends relying on the test framework's native assertion vocabulary rather than custom helpers:

  • Consistency. Custom assertion helpers "promote different assertion syntax" — every bespoke checker is one more dialect teammates must learn before they can read or extend a test.
  • Composability. Native assertions are small and orthogonal; the author of the next test can mix and match them freely instead of bending a rigid helper to a new scenario.
  • Better failure output. pytest rewrites plain assert statements to show rich diffs of both sides. Logic buried in loops and set-comparisons collapses to "assert False" plus whatever message the author remembered to write.

Source: nodejs-testing-best-practices, Section 4 — Test Anatomy.

3. Tests are too long and carry details unrelated to the case

Important
More info

Where: e.g. tests/citations/test_consecutive_ordering.py:117-142 (26 lines), test_consecutive_ordering.py:98-114, tests/citations/test_create_child_reference.py:6-18

Individual tests run well past a digestible size and include data that has nothing to do with the behavior under test. test_send_citations_events_emits_one_object_ref_per_citation spans 26 lines with ~12 assertions covering event type, sub-type, id, label, params, paragraph data and ordering. The _make_parent factory pins nine fields (homepage_title, public_label, source_url…) even when a test only cares about one of them — so a reader can't tell which inputs actually drive the expected output.

Why this matters

  • Keep tests very small — the guide's rule of thumb is no longer than ~7 statements per test. Anything bigger stops reading as documentation of one behavior.
  • Include only the data that matters. Extraneous fields and setup noise make it "harder to troubleshoot and understand" — when the test fails, every irrelevant detail is a suspect the reader has to rule out.
  • Tests are executable docs. A focused, concise test tells the next developer exactly what input produces what outcome; a 26-line test with a dozen assertions tells them to go read the implementation instead.

Source: nodejs-testing-best-practices, Section 4 — Test Anatomy.

4. Tests are not focused on specific scenarios — titles don't follow when/then

More info

Where: e.g. tests/citations/test_clean_citation_text.py:9 (test_strips_atx_heading_markers), tests/compliance_assistant/workspace_artifacts/test_artifact_aggregation_validation.py:7 (test_validate_aggregations_maps_avg_to_average)

Because many tests bundle several behaviors into one body (see finding 3), their titles can only describe the mechanism, not a scenario. Names like test_strips_atx_heading_markers or test_send_citations_events_emits_one_object_ref_per_citation state what the code does, not when a condition holds and then what outcome is expected. A failing test name should read as a spec sentence — e.g. test_when_titles_are_duplicated_then_each_gets_an_incrementing_ordering — so the report alone tells you which business rule broke.

Why this matters

  • One test = one interaction. The guide prescribes that each test cover "a single interaction" — a single scenario with a single expected outcome — structured with the AAA pattern (Arrange, Act, Assert).
  • Three-part / when-then naming. Titles should encode the unit under test, the scenario ("when…"), and the expectation ("then…"). "Descriptive titles document expected behavior" — the test report becomes a readable spec, even for someone unfamiliar with the codebase.
  • Focused scenarios fail precisely. When a multi-behavior test fails, the title can't tell you which of its many assertions broke; a when/then-scoped test pinpoints the broken rule from the CI summary alone.

Source: nodejs-testing-best-practices, Section 4 — Test Anatomy.

5. The Tartlet query tool is not covered besides one/few happy paths

More info

Where: src/tools/new_tartlet_client/ — filter_tool.py, capabilities.py, and dozens of tool modules under new_tools/ (grants, tickets, stakeholders, workflows…) with no dedicated tests under tests/

The query/filter tool surface is large — dozens of tool modules plus the filtering capabilities layer — yet the only exercise it gets flows through recorded happy-path replays. There are no tests for empty results, malformed filters, unknown IDs, partial batch matches, or pagination edges. The behaviors most likely to break in front of a user are exactly the ones with zero coverage.

Why this matters

  • Go beyond the happy path. The guide ("Test the five potential outcomes", "Simulate network chaos") requires checking not only successful responses but errored and anomalous ones — that is where resilience is proven or disproven.
  • Happy-path-only suites give false confidence: they validate the demo scenario while the agent, at runtime, queries arbitrary subsets, bad IDs, and unexpected combinations.

Source: nodejs-testing-best-practices — "Test the five potential outcomes", "Simulate network chaos".

6. Tools coverage is limited — bad responses are not surfaced

Important
More info

Where: tests/tartlet_mock/tenant_responses.py:146-152 — recorded 5xx entries are deliberately skipped ("server flake at recording time")

The mock router doesn't just lack error scenarios — it actively filters them out: any recorded 5xx response is dropped from registration, so in test mode the tools can never receive a server error. Timeouts, slow responses, 4xx validation failures, and malformed bodies are equally unrepresented. How each tool behaves when Tartlet misbehaves — retry, raise, surface a readable message to the agent — is untested everywhere.

Why this matters

  • "Check not only errored responses (e.g., HTTP 500 error) but also network-level anomalies like slow and timed-out responses." Error handling is part of the contract; it deserves the same coverage as data shape.
  • The five-outcomes framework includes observability and error handling as first-class outcomes to assert — a suite that physically cannot produce a bad response can never cover them.

Source: nodejs-testing-best-practices — "Simulate network chaos", "Test the five potential outcomes".

7. No network interception of outgoing calls

More info

Where: src/tools/tartlet_client/factory.py — the respx router is injected as an httpx.MockTransport into the Tartlet client only

The replay mock works by swapping the transport inside one client. Nothing intercepts or denies network traffic at the process boundary: any other code path — LLM/Vertex calls, other HTTP clients, a new integration someone adds next month — goes straight to the real network during tests, silently. There is no equivalent of a deny-all default.

Why this matters

  • "Deny all outgoing requests by default" — the guide recommends instructing the interceptor to block and warn on any outgoing HTTP request that was not explicitly mocked.
  • It protects isolation and catches forgotten integrations: a test that quietly hits a real service is flaky, slow, potentially costly (real LLM calls), and can mutate real data — and you only find out in production or on the bill.
  • In this stack: enable respx's global mock mode (or a conftest-level guard) so any unmatched outgoing request fails the test loudly, instead of intercepting only the one client that was wired for it.

Source: nodejs-testing-best-practices — "Deny all outgoing requests by default".

8. One god base test setup instead of small per-mission overridable fixtures

More info

Where: tests/tartlet_mock/tenant_responses.py:89-118 — install_tenant_responses_once is a process-lifetime singleton (module-level _installed globals); there is no conftest.py and no pytest fixtures anywhere in tests/

The entire mock world is built once per process, from everything recorded for the tenant (~600 fixture files), and is shared by whatever runs afterwards — install-once, never reset, no per-test variation. A test cannot say "for this scenario, this endpoint returns an empty list / a 500 / a different stakeholder"; it inherits the full god-setup or nothing. The opposite of small, mission-scoped fixtures that each test composes and overrides.

Why this matters

  • "Each test should act on its own records only." The guide reserves global seeding for metadata/context only — scenario data belongs to the test that asserts on it.
  • The Domino effect: "Understanding why test num #27 failed demands reading the 26 tests before" — a shared world couples every test to every other; one re-recording changes the ground truth under the whole suite at once.
  • Overridability is the feature: small per-test fixtures (a base router fixture + per-test route overrides) are what make the error-path and edge-case tests of findings 5–6 even possible to write.

Source: nodejs-testing-best-practices — "Each test should act on its own records only", "Only metadata and context data should get pre-seeded".

9. Some tests assert on a response that comes from a mock — the loop isn't closed

Important Discussion call
More info

Where: the overall test loop — recorded fixtures in, assertions on what the mock returned out

Some of the tests assert on a response that ultimately originates from a mock we wrote ourselves: the suite records Tartlet's answers, replays them, and then verifies the code returns… those answers. Something is not complete in the overall loop — it's hard to put the finger on exactly where, but the suspicion is that the suite is partly testing the mock rather than the system. This one is a discussion call for the team, not a prescribed fix.

Why this matters

  • "When relying on mocking-only — these issues pass unnoticed in testing and might fail in production once they meet the real API." Asserting against your own canned data validates the replay plumbing, not the contract.
  • Possible directions to discuss: contract testing or generating the client from an OpenAPI spec, schema-validating recordings against the live API on a schedule, or a thin layer of real-Tartlet smoke tests that anchor the recordings to reality.
  • The guide's "record real outgoing requests for awareness" practice is the constructive half: recordings are valuable for realism, as long as something else keeps them honest.

Source: nodejs-testing-best-practices — "Code against a strict API provider contract", "Record real outgoing requests for awareness".

1. A conditional expression inside an assertion makes it always pass

Important D.7 · A.13
More info

Where: tests/citations/test_consecutive_ordering.py:137

This is the one finding in this review that is an actual bug rather than a convention mismatch:

assert emitted_event["label"] == "Dup" if reference_id != "parent_2" else "Other"

Python's conditional expression binds looser than ==, so this parses as:

assert ((emitted_event["label"] == "Dup") if (reference_id != "parent_2") else "Other")

For parent_2, the assert evaluates the bare string "Other" — which is truthy — so the third citation's label is never checked at all. If the code under test emitted label="Dup" (or garbage) for parent_2, this test would still pass.

Rules violated

  • D.7 "Avoid custom coding, loops and list comprehensions in the assert phase, stick to built-in assert with full-object equality." This bug is precisely why the rule exists — logic inside an assertion can silently change what is being asserted.
  • A.13 Totally flat: no conditional logic anywhere in a test. A flat assert emitted_event["label"] == expected_label per case, or a full-dict equality check, cannot mis-parse.

Sources: references/assertions.md §D.7, references/the-test-anatomy.md §A.13.

2. Loops and branching inside test bodies — the totally-flat rule

A.13 · Rule 3
More info

Where: tests/citations/test_clean_citation_text.py:101-104 (a for + if + generator-expression scan), tests/citations/test_consecutive_ordering.py:35-38, :64-66, :79-80, :101-104, :125-128, :132-139 (loops in both Arrange and Assert phases)

Rule 3 of the rulebook's "6 Most Important (!) Rules" states: "Anything beside flat statements is not allowed - no if/else, no loops, no try/except, no print." Seven test bodies in the citations suite contain loops; several iterate inside the assert phase (for marker in markers: assert …), and one combines a loop, an if, and a next() generator scan into a single assertion (test_full_bug_repro_does_not_produce_setext_h2).

Why this matters

  • When a looped assertion fails, pytest reports the failure without telling you which iteration broke — the reader has to re-run with a debugger.
  • Loop-driven arrange phases (test_consecutive_ordering.py:101-104, :125-128) hide how many records exist and what their ids are; flat statements (parent_0 = …, parent_1 = …) make the 🔫 smoking gun visible.
  • Finding 1 is the direct consequence: once logic is allowed into a test, assertion bugs follow. The rulebook's stated goal is keeping test complexity "ridiculously low" so tests never become another system to maintain.

Flat alternatives: assert on a full expected list (assert [r.consecutive_ordering for r in references] == [0, 0, 1, 1, 2] is still a comprehension — better: compare the whole objects list built by a factory), or split per-case into separate tests / pytest.mark.parametrize.

Sources: references/the-test-anatomy.md Rule 3, §A.13; references/assertions.md §D.7. See also nodejs-testing-best-practices Section 4 — keep each test "a single interaction," not a scripted scan.

3. Tests target private internals instead of user-facing behavior

Important B.23 · Rule 4
More info

Where: every test file — processor._clean_citation_text(…) (test_clean_citation_text.py, all 12 tests), processor._apply_consecutive_ordering(…) / _build_citation_event_entry / _send_citations_events / _build_citation_object_ref_event (test_consecutive_ordering.py), and _validate_aggregations imported directly from artifact_handlers (test_artifact_aggregation_validation.py:4)

Nearly the whole suite calls underscore-prefixed private methods, and several tests arrange by mutating private state — e.g. appending directly to processor._pending_citations (test_consecutive_ordering.py:104, :128). Only create_child_reference (a public function) is tested through its real surface.

Rules violated

  • B.23 "Don't test implementation details… check user-facing behavior like response payloads, return values, or external side effects."
  • Rule 4 of the 6 critical rules: given the test scope, cover all layers of the code under test — never enter through an internal method when the user-visible entrance (the stream-processing call that triggers citation events) exists.
  • testing-strategy.md — "What to Test: External Outcomes Only… We test what the user sees and what the system emits — never how the code is structured internally."

Concretely: renaming _apply_consecutive_ordering or moving dedupe logic into the event builder would break a dozen tests while user-visible behavior is unchanged. The observable contract here is the emitted callback events — tests should feed text with citation markers through the processor's public streaming API and assert on what the callback received.

Sources: references/the-test-anatomy.md Rule 4, §B.23; references/testing-strategy.md. See also nodejs-testing-best-practices Section 1 — test via the component's public API so refactors don't shatter the suite.

4. No component test exists — and the heaviest test infra has zero consumers

Strategy
More info

Where: the whole tests/ tree (4 unit-test files) vs. tests/tartlet_mock/ (311-line router + 609 recorded JSON fixtures)

testing-strategy.md names this type (its "flow test" — a component test in this project's vocabulary) — entrance door (webhook, CLI, API) → visible outcome, with only external systems mocked — as "Default and preferred," and requires at least one before merging any multi-layer change. The new suite contains only unit tests of private functions; there is not a single test that exercises an entrance door.

More striking: no test consumes the Tartlet replay infrastructure at all. A repo-wide search shows install_tenant_responses_once / TARTLET_TEST are referenced only from src/ (the client factory and the evaluation credentials loader) — never from a test. The largest piece of the new testing infra (the router plus 609 recorded fixtures) currently serves manual/eval runs only, while the automated suite it was presumably built for doesn't exist yet.

Why this matters

  • The replay router is exactly the seam a component test needs (E.9-style network interception at the process boundary) — the strategy's preferred test type is one fixture away, yet uncovered.
  • Until a component test exists, the recorded fixtures rot silently: nothing fails when they drift from the live Tartlet contract (this compounds tab-1 finding 1).
  • The unit tests that do exist cover string cleaning and dedupe ordering — none of them would catch a broken end-to-end citation flow.

Sources: references/testing-strategy.md ("Supported test types", "When to write each"). See also nodejs-testing-best-practices Section 1 — component/flow tests as the primary strategy, unit tests as the supplement.

5. Hand-rolled in-file helpers instead of data factories

C.3 · C.4 · C.5 · A.28
More info

Where: _make_parent (test_create_child_reference.py:6-18), _make_reference / _make_processor_with_children (test_consecutive_ordering.py:10-29), _make_processor (test_clean_citation_text.py:5-6)

Each test file grew its own private builder, which mismatches the data rules on four axes:

  • A.28 🏗️ The structure principle — helpers belong in a dedicated nearby file (factories.py), "not within the test file itself." Three files now have three diverging ways to build the same Reference.
  • C.4 Factories must accept per-field overrides. _make_parent(**overrides) does; _make_reference(reference_id, user_facing_title) hard-pins the other five fields, so a test that cares about e.g. source_url can't use it.
  • C.5 / C.10 Universal data should come from faker-style realistic generators; the suite uses fixed strings ("Slice Knowledge", "excerpt", id "32") everywhere, so every test runs against the exact same frozen values.
  • C.7 Factory params need type hints matching the code under test — **overrides is untyped.

This also produces a 🔫 A.4 smoking-gun break: test_child_reference_id_includes_parent_id_and_citation_index asserts child_id == "32_7" (test_create_child_reference.py:59) — the "32" half of that expectation lives in the factory's hidden defaults, not in the test's arrange phase. The reader can't see where the asserted value comes from. assert child_id == f"{parent.reference_id}_7" would close the loop.

Sources: references/the-test-data.md §C.3–C.10, references/the-test-anatomy.md §A.4, §A.28.

6. Test names skip the when/then pattern; AAA phases are invisible

A.1 · A.5
More info

Where: all 33 tests across the four files — e.g. test_strips_atx_heading_markers, test_consecutive_ordering_starts_at_zero_for_duplicates, test_validate_aggregations_maps_avg_to_average

A.1 prescribes test_when_<case>_then_<expectation>. Zero tests follow it. Most names state a mechanism (test_strips_…) rather than a scenario + expectation (test_when_text_contains_atx_headings_then_markers_are_removed). This is the rule-ID counterpart of tab-1 finding 4.

A.5 requires visible Arrange/Act/Assert phases — either # Arrange/# Act/# Assert comments or blank lines before the 2nd and 3rd phases. The citations tests run arrange, act, and assert together with no separation at all (e.g. test_clean_citation_text.py:9-12 — three packed lines). Notably test_artifact_aggregation_validation.py does separate its phases with blank lines — it's the in-repo example the citation tests should match.

Why this matters

  • A failing test name should read as a broken spec sentence in the CI summary, pinpointing the rule without opening the file.
  • Phase separation is what makes a 4-line test scannable: which line is the trigger, which lines are the contract.

Sources: references/the-test-anatomy.md §A.1, §A.5. See also nodejs-testing-best-practices Section 4 — "Stick to unit testing best practices": AAA structure, single interaction per test.

7. The Tartlet mock is a hidden, process-global singleton that is never reset

Important A.15 · E.5 · E.7 · B.28
More info

Where: tests/tartlet_mock/tenant_responses.py:89-118 (module-level _installed / _installed_router globals), src/tools/tartlet_client/factory.py:20-41 (env-var activation + module-level _test_transport), src/tools/tartlet_client/test_mode_env.py

The replay router violates the mock-hygiene rules in three stacked ways:

  • 🥨 A.15 The breadcrumb principle / E.5 — "Define mocks directly in the test… Never hide mocks in external files where they mysteriously alter behavior." Here the mock isn't even in a conftest.py: it is activated by an environment variable (TARTLET_TEST=true) read deep inside production code. A test (or a future flow test) that constructs a Tartlet client gives no visible signal that every HTTP response is canned.
  • E.7 / B.28 — mocks must be reset between tests. install_tenant_responses_once is deliberately once-per-process (_installed = True, never unset), and factory.py caches _test_transport in a module global. The first caller's tenant wins for the process lifetime; a second test using a different tenant id silently receives the first tenant's recordings. Nothing cleans up.
  • Structural inversion: src/tools/tartlet_client/factory.py:20 does from tests.tartlet_mock.tenant_responses import … — production code importing the test package. Production deploys now depend on tests/ being importable, and the test/prod boundary the rules lean on (mock only at external seams, keep test machinery out of the app) is dissolved.
  • A.23 (in spirit) — install_tenant_responses_once uses bare assert statements inside helper code (tenant_responses.py:98-99); assertions belong in test functions, and these would vanish under python -O.

The compliant shape: a per-test (or per-session, explicitly scoped) pytest fixture that builds the respx router and injects the transport — making the mock a visible breadcrumb in each test that uses it, resettable, and removing the env-var seam plus the src → tests import entirely.

Sources: references/mocking.md §E.5, §E.7; references/the-test-anatomy.md §A.15, §B.28.

8. Membership and fragmented assertions instead of full-output equality

D.11 · D.13 · A.10
More info

Where: tests/citations/test_clean_citation_text.py:19-21, :28-30, :37, :44-48, :55; tests/citations/test_consecutive_ordering.py:106-114, :130-142

Many tests assert with substring membership — assert "---" not in cleaned, assert "before" in cleaned — instead of comparing the full cleaned output:

# current (5 partial checks, weak failure output)
assert "***" not in cleaned
assert "___" not in cleaned
assert "before" in cleaned
...

# per D.11 / D.13 (one check, full diff on failure)
assert cleaned == "before\nmiddle\nafter"
  • D.13 — "Prefer assertions that provide full comparison details on failure… not assert expected_value in actual_list which only reports membership." A membership miss prints only the haystack; an equality miss prints a precise diff.
  • D.11 🎯 The focused principle — one full equality subsumes the whole batch. It also closes real gaps: test_strips_setext_h1_equals_underline (:37) checks only that "===" disappeared and would pass even if the heading and paragraph text were destroyed along with it.
  • A.10 — assertion-count cap. test_send_citations_events_emits_one_object_ref_per_citation carries ~12 assertions (plus the looped batch from finding 2); asserting full expected event dicts (built from the factory per D.15) collapses them to one or two.

Sources: references/assertions.md §D.7–D.15, references/the-test-anatomy.md §A.10. Complements tab-1 finding 2 (custom assertion logic) with the rulebook's concrete rule IDs.

9. 🎯 Two tests blow past the 12-statement cap

A.3 · Rule 1
More info

Where: tests/citations/test_consecutive_ordering.py:117-142 (~19 statements) and :98-114 (~16 statements)

A.3 / Rule 1 of the "6 Most Important (!) Rules" — 🎯 The focused principle: a test may have no more than 12 statements (this project's cap). Counting flat statements (a multi-line call counts as one, loop bodies count per statement):

  • test_send_citations_events_emits_one_object_ref_per_citation — ~19 statements: 2 to construct, a 3-statement arrange loop, the act call, then 2 top-level asserts, a 7-statement assert loop, and 3 trailing asserts. Roughly 160% of the cap.
  • test_send_citations_events_emits_consecutive_ordering_in_callback — ~16 statements: 2 to construct, a 3-statement arrange loop, the act call, then 9 assert/extract statements.

Every other test in the suite fits the cap (the next-largest are at 11: test_consecutive_ordering_tracks_each_duplicate_group_independently and test_build_citation_object_ref_event_places_metadata_in_data — compliant but worth watching).

How to get under the cap

  • The arrange loops collapse to flat factory calls (finding 5) — two statements instead of four.
  • The assert batches collapse to one or two full-object equality checks against expected event dicts (finding 8) — which also removes the loop that hides the finding-1 bug.
  • If a behavior still doesn't fit in 12 statements, it is two behaviors — split the test (each currently checks event shape and ordering and labels).

Sources: references/the-test-anatomy.md Rule 1, §A.3 (cap: 12 statements for this project).

10. The test runner is undeclared — pytest is missing from requirements and there is no pytest config

Infra
More info

Where: repo root — no pyproject.toml, no pytest.ini, no setup.cfg; requirements.txt pins respx==0.22.0 but contains neither pytest nor faker

The suite's mocking dependency made it into requirements.txt (respx==0.22.0) but the runner itself did not — there is no pytest pin anywhere, and no faker for when the data factories (finding 5) are introduced. There is also no pytest configuration file at all, which has two concrete consequences:

  • Unreproducible runs. Whoever runs these tests depends on a globally-installed pytest of unknown version; a teammate or CI image without one can't run the suite from a clean checkout, and version drift between machines changes collection and assertion-rewriting behavior silently.
  • Unbounded collection scope. With no testpaths setting, pytest discovers test_*.py from the rootdir across the whole repository — which is what turns the stray runner scripts in finding 13 from a naming nitpick into an operational risk.

Fix: add pytest (and faker) to a pinned requirements file, and a minimal pyproject.toml [tool.pytest.ini_options] block with testpaths = ["tests"].

Context: references/test-commands.md assumes well-defined, repeatable run commands for the suite; none can exist while the runner itself is undeclared.

11. Bare MagicMock() without spec — mocks that survive contract drift

E.3
More info

Two data-shape rules are missed together:

  • B.3 🚀 The extra mile principle — "Testing a grid filter? Also assert an item that should NOT be shown." 13. Ad-hoc LLM runners named test_*.py sit in scripts/ — inside pytest's collection path

Strategy · A.13
More info

Where: scripts/test_country_detector.py (196 lines), scripts/test_platform_classifier.py (135 lines)

Two manual "test runner" scripts call real LLM endpoints (the QUERY_CHECK model on Vertex), loop over hard-coded case tables, count pass/fail, and print markdown result tables. As tests they violate the anatomy rules wholesale (loops, prints, no assertions, no AAA — A.13), and they belong to none of the three sanctioned test types in testing-strategy.md — they are closest to evaluations, which this repo handles elsewhere (src/evaluation/, scripts/run_compliance_evals_xlsx.py).

Why the naming is the real problem

  • They match pytest's default test_*.py discovery pattern, and with no pytest config restricting testpaths (finding 10), they sit squarely in collection scope. Today they define no test_ functions, so nothing executes — but pytest still imports them at collection time, dragging in pydantic_ai and the provider-factory stack; any module-level env requirement added there will fail the entire suite run.
  • One renamed helper to test_… away from disaster: if either script ever gains a test_-prefixed function, CI starts making real Vertex calls.
  • The name lies to the reader: "the tests" in scripts/ are not part of any automated quality gate.

Fix: rename to check_country_detector.py / check_platform_classifier.py (or move under an eval folder), and set testpaths = tests in a pytest config so collection scope is explicit.

Sources: references/testing-strategy.md (supported test types), references/the-test-anatomy.md §A.13, references/test-commands.md (run commands must be config-defined, not ad-hoc scripts).
