OPA basics, for newcomers

What is OPA, and what is this actually about?

OPA (Open Policy Agent) is an off-the-shelf engine for writing "rules that decide things" as code, kept separate from the main application. Instead of burying a rule like "warn the user if this grant might have a tax problem" inside application code, you write it as a small, declarative rule in OPA's own language, called Rego. The app feeds OPA some data (a "grant", a "stakeholder", etc.), and OPA answers yes/no (or attaches structured info) for each rule.

In this codebase, the opa/ folder holds ~900+ of these Rego rule files, mostly under opa/compliance/. Each rule is Slice's codified version of a real compliance/tax/legal requirement — e.g. "flag this grant if it's under Israeli Section 102 tax treatment and it has double-trigger acceleration." When the conditions match, Slice shows the user a compliance alert banner in the product. Every such rule has an internal identifier called a ruleId (e.g. israel102GrantDoubleTrigger) — a technical name, not something a customer ever sees; what the customer sees in the product is just the alert's plain-language title.

The problem this PR solves: when a customer opens a support ticket asking "why am I seeing this warning on my grant?", someone (a support/CS person, or SliceAI — Slice's in-product AI assistant) has to answer in plain English. Today that means an engineer or support person manually digs through the Rego file for that rule to figure out every condition it checks. This PR automates that lookup: give the new agent one ruleId, and it reads the matching Rego file(s), lists every condition in plain business language, and writes a customer-safe explanation — while deliberately never mentioning the ruleId, the file path, the word "OPA"/"Rego", or any raw internal field name in what gets shown to the customer (those are meaningless, and arguably inappropriate, to expose outside engineering).

Analogy: think of OPA/Rego rules as a big rulebook of "if X and Y, then flag this" written in a technical shorthand only engineers read. This PR adds a translator that takes one rulebook entry and rewrites it as a paragraph a customer or support agent can actually understand — without pointing at the rulebook itself.

What is it about

A read-only "explain one compliance alert" agent for SliceAI tickets

This PR adds a new Cursor agent + skill + slash command bundle: given a single compliance-alert ruleId, it investigates the matching .rego policy under opa/compliance/ and produces a plain-language, customer-safe explanation — title, all trigger conditions, when it stays silent, and next steps — with ruleIds, file paths, OPA/Rego, and data-model field names deliberately scrubbed from the output. It's meant to be called from SliceAI ticket workflows and by CS/account teams, one alert at a time (explicitly not a jurisdiction/catalog browser).

Core mechanics it encodes
  • One alert per request, no catalogs. Every layer (agent prompt, command doc, skill body, templates) repeats: require a ruleId; never list alerts by country/jurisdiction; ask rather than guess when ambiguous.
  • Two-layer model. "Investigation" (ruleId, .rego, logic blocks, tests, input JSON) is internal-only; the "Deliverable" is scrubbed prose for the ticket/CS/customer.
  • Strict output scrub list. No ruleIds, UUIDs, file paths, OPA/Rego/WASM/compliance-engine vocabulary, or raw data-model field names — with an explicit internal-term → customer-phrasing table.
  • Grounded policy map. policy-tracing.md and find-rule.sh point at real paths (opa/compliance/, opa/business_logic/, opa/legal_tax/, apps/backend/compliance-engine/test) — verified these all exist and the test search pattern (const RULE_ID = '...') matches real test files.
  • Escalation path. If the policy logic itself looks wrong, the skill tells the operator (not the ticket) to use the existing policies-agent — a sensible, non-duplicative handoff to the agent that actually edits .rego.
