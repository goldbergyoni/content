The testing strategy asks for too much

Severity: Very high

We use six different kinds of tests today — and that is before adding AI evaluations. Each kind needs its own tools, its own fakes, and its own rules. That is a lot of technique and expertise to ask of every developer, and every AI agent, that writes a test. The mental model is heavy, and heavy models get followed loosely.

Alternative: write only three kinds of tests — unit, component, and evaluation. That is the minimum this project needs, and it is a model anyone can hold in their head.

More detail

The six kinds in the repo today, each with a different shape and different fakes: pure engine unit tests, LLM-port wiring tests, py_commons infrastructure tests, component tests, one full-job use-case test, and CLI tests. A contributor has to learn which one to reach for, where it lives, and what it is allowed to assert — six times over.

Three types cover the real risk with far less to learn:

  • Unit — for pure logic with real branching (the scoring and equity maths).
  • Component — the main tier: enter through the API, run against real infrastructure, check every exit door.
  • Evaluation — for the one thing unit and component tests cannot judge: whether the AI's answers are actually good.

Fewer types means faster onboarding, a rule an agent can follow reliably, and less test code to maintain.

Our main tests cut through the middle of the code

Severity: Very high

Our component tests start halfway inside the code, not at the front door. They call inner functions directly, run on fake infrastructure, and check only one or two of the code's outputs. So the real entry point — the API — and most of the real exits are never exercised.

Alternative: enter through the API, run against real infrastructure in a docker-compose (a real Mongo and Redis), and assert on all the exit doors: the response, the saved data, outgoing calls, and queued messages.

More detail

A good component test drives the whole component as a customer would — in through the HTTP request, out through every observable effect — with only truly external systems (the LLM) faked. Ours do the opposite:

  • They import a subset of folders (extractors, persistence, localization) and call those functions directly.
  • They hand the code an already-parsed answer, use an in-memory fake Mongo, and never start the web server.
  • They assert on a small slice of the output, so most of the code's real exit doors go unchecked.

The cost is concrete: FastAPI routing, request validation, and error handling are skipped entirely (20 routes, 0 tests), and comparison plus external-fetch — half the pipeline — never runs in any test. When the test sits in the middle of the code, the parts most likely to break are the parts it can never see.

No real database is used in tests

Severity: Very high

Our tests run against a fake Mongo that does not support everything real Mongo does. To fill the gaps we wrote our own copy of Mongo's query logic inside the test setup, so the tests check our idea of Mongo instead of Mongo itself.

Alternative: use a real Mongo in a docker-compose (a throwaway container), and install the production schema the production way.

More detail

This can go wrong in two ways: the extra query logic is more test code to maintain, and tests can pass on things real Mongo would reject — a false sense of safety.

The screen customers actually read is built from many stitched-together queries, and all of them are only checked against our copy of Mongo, never the real one. Rules that real Mongo enforces — required fields and unique values — are not enforced by the fake at all, so a test can save data that production would refuse.

A real database in the test would remove the hand-written logic and add only a few seconds to the run.

There are no AI evaluations

Severity: High

Nothing measures whether the AI actually pulls the right data out of a document. Our tests check that we handle a correct answer correctly — they never check that the model returns a correct answer in the first place. So we know the code is correct; we do not know the product is good.

Alternative: add an evaluation suite — for example DeepEval or a LangChain-based harness — with labelled documents and proper evaluation practices, run on a schedule.

More detail

Real confidence in an AI product is about quality, not only correctness. Correctness is "the code did what the code says." Quality is "the extraction was right." Only evaluations measure the second one: golden documents, the expected extraction for each, a score, and a threshold that has to be met — run nightly rather than on every pull request, because it costs money and it varies run to run.

Without it, prompt edits and model swaps are ship-and-pray. The team already pins claude-opus-4-8 for one document type on the belief that only it extracts dense tables reliably — and nothing would tell them if that stopped being true, or if a cheaper model caught up. Start small: one document type, ten labelled documents, field-level match, a score posted to Slack.

200 tests, but they catch about a third of bugs

Severity: High

We ran mutation testing — deliberately break one line of code, then see if any test fails. Out of thousands of planted bugs, only about a third were caught. Some layers are tested well; others are barely tested at all. This is worth a closer look.

A handful of real bugs the current suite would let through:

  • A database lookup could search for the wrong thing (an empty query) and stay green.

Outside services are faked too loosely

Severity: High

We fake outside services inside our own code instead of at the network level, so the code that actually builds and sends the request never runs in a test. Slice Tartlet, a sister service we depend on, is swapped out as a plain function rather than a real call over the wire.

Alternative: fake these services at the network level (respx is a good candidate), and add a typed check (for example from their OpenAPI spec) that flags any drift between their API and ours.

More detail

When we fake at the network level, more of our own code is part of the test — the request building, the response parsing, the error handling all run for real. Faking a function skips exactly the layer that tends to break.

The bigger risk is drift: if the other team renames a field or changes a response, we only find out in production, and matching quietly gets worse without any error. A typed contract, generated from their API description, would catch that change in a test instead.

Tests can be simpler

Severity: High

Some tests are long and check the result one field at a time, which hides what the test is really about. Two things make them shorter and clearer: shared data factories for the inputs, and comparing the whole result at once.

Alternative: add data factories for test inputs, compare the whole result to one expected object, and read data back through the API rather than straight from the database.

More detail

A few tests run to 50–75 lines, most of it building the input by hand before a long list of field checks. The point of the test is buried under that setup. The field-by-field style looks like this:

Missing: data factories

The team's own rules/the-test-data.md describes a data factory — one builder per data type (e.g. build_finding) that returns realistic default data using faker, and lets each test override only the fields it cares about. We don't have them: no factories.py, no data folder, and faker is not installed.

With factories, a test names only the two or three fields that matter to it — the "smoking gun" — and everything else is a sensible default. The 60-line setup collapses to a couple of lines, and the reader sees instantly what the test is actually about.

Better pattern: don't reach into the database

To check what was saved, our tests query the database directly, asserting on raw collection and field names:

services/ai_documents/tests/test_use_cases/test_extractors_use_case.py:35white-box coupling
db = mock_environment.db

This is white-box coupling: the test is tied to how data is stored internally, so renaming a collection or a field breaks the test even though nothing actually changed. The rules say so too (testing-with-database.md G.9). Read the result back through a higher level — a service or the API — and the test checks behaviour, not internals.

Some unit tests are filler — they test our wiring, not our logic

Severity: Medium

A few tests copy what the code does, then check the code matches the copy. That always passes — even when the code is wrong. It is low-value filler: it inflates our coverage numbers and adds maintenance, while catching nothing.

Alternative: write unit tests only for real decision logic — the heavy algorithms — not for the plumbing and wiring of the system.

More detail

The clearest case rebuilds a hash the exact same way production does, then asserts the two are equal:

This passes for any version of the code, including a broken one, because both sides run the same logic. The thing that actually matters — the hash changes when a prompt changes, and stays the same when nothing changes — is never checked.

Two concrete costs, both real:

  • It inflates coverage. The test runs the production lines, so our coverage tool marks them "tested" — a green number that hides a genuine gap. Mutation testing shows the same lines let faults through.
  • It adds maintenance. Because it mirrors production, every change to the hashing has to be copied into the test too — effort spent on a test that can never fail for the right reason.

A pinned golden hash plus one "change the prompt, expect the hash to change" test would be more valuable and half the size. The rule of thumb: unit-test the heavy decisions, never the wiring.

What this system does

mono-ai is the document-intelligence pipeline behind Global-Slice's equity and cap-table platform. Customers hold piles of legal paperwork that describe who owns what: grant letters, exercise notices, share certificates, board approvals, equity plans, share registers, secondary share-purchase agreements. That paperwork is the truth, but it is unstructured — and the equity platform needs rows in a database, not PDFs.

The service closes that gap in four moves. It classifies each document (what kind of paper is this?), extracts a typed, schema-validated record from it with an LLM, localizes every extracted field back to a bounding box on the PDF page so a human reviewer can see the evidence highlighted where it was found, and finally compares the extracted record against the customer's live equity entities — grants, shares, equity plans, vesting schedules, share classes — fetched from the internal system of record, a service called Slice Tartlet. The output of a job is a structured record, a ranked top-k list of candidate matches with scores, a set of bounding boxes, and flags such as "this PDF contains hidden text."

Around that core, an ops surface has grown. POST /v1/link-audit answers a reconciliation question: the human who linked this document to that grant — was that the AI's best match too? It returns a verdict of confirmed, suspect, or no-match. POST /v1/score-explain opens up any score and shows the per-field distance, weight, and contribution that produced it, optionally with an LLM-written narrative. There is also an XLSX export and a standalone table-normalization endpoint. In other words: the product is not just extraction, it is auditable extraction, and a good deal of the codebase exists to make the AI's decisions explainable to a human.

Architecturally it is one deployable service and five libraries, in a Python 3.12 uv workspace. The service (services/ai_documents) runs as three processes: a FastAPI API, a Taskiq worker, and a singleton reaper daemon. The libraries are split with real discipline — comparison_engine, table_normalization, and field_localization_engine are strictly pure, I/O-free, and port-injected; equity_domain layers the equity vocabulary on top of the generic comparison engine; and py_commons holds every piece of infrastructure (the LLM gateway, Mongo, GCS, Descope auth, Slack, OpenTelemetry). The layering is hexagonal and, notably, honest: every out-of-process dependency sits behind a Protocol in a ports.py, every concrete adapter lives under integrations/, and concretes are constructed in exactly one place — core/containers_lifecycle.py.

Technologies

Runtime & web

Python 3.12 · FastAPI · Uvicorn · Pydantic v2 (pydantic-settings) · uv workspace with a single root lockfile.

Async work

Taskiq over a Redis stream broker, with a Redis result backend. Redis-Streams auto-claim is deliberately disabled (a ~10-year idle timeout) so the custom reaper is the sole retry path.

AI

claude-sonnet-4-6 for classification and most extraction; claude-opus-4-8 only for secondary SPAs ("dense image tables that only opus extracts reliably"); claude-haiku-4-5 for comparison string-distance and score narratives; gemini-2.5-pro exclusively for bounding-box vision work. Provider chain: Anthropic-on-Vertex, falling back to the Anthropic API.

Data & ops

MongoDB (22 collections) · Google Cloud Storage · Langfuse for LLM cost/traces · OpenTelemetry → Coralogix · Slack webhooks · Descope for outbound M2M auth.

The layers

A request enters through a route, is validated by a DTO that forbids unknown fields, is handed to a use-case Protocol (the dependency-injection seam that makes routes swappable in tests), which calls an application service, which speaks to the domain and to ports. Adapters implement those ports. Nothing below the ports layer knows what a database or an LLM is.

3. The daemon

A singleton process (replicas=1, strategy: Recreate) running the reaper loop every 60 seconds: a heartbeat reap and a stuck-QUEUED reap. Type 6 — CLI tests red

cli/ai_documents/tests — 8 tests that have never run

Eight perfectly reasonable tests of file discovery and document building. They cannot be collected. Importing the CLI pulls in equity_domain.tax_treatment, which builds a dynamic enum at import time from a JSON cache file that only the Docker entrypoint creates. Every other package works around this with a conftest that writes the cache first; the CLI has no conftest, so collection dies with RuntimeError: Tax treatment cache missing. Nobody has noticed, because the CLI package is not in the pre-commit hook and there is no CI test job.

The test infrastructure

The LLM fake

AsyncMock(spec=LlmProvidersGateway) in the root conftest, with a set_parsed() helper. The response is never parsed from raw text — the test hands over a Pydantic model a developer wrote by hand. In the full-job test a side_effect dispatches by response_model, so one fake serves several extractors. No API key is ever needed.

The database

mongomock-motor, in-memory. No testcontainers, no docker-compose, no real Mongo anywhere. And test_use_cases/conftest.py:64-165 monkeypatches roughly 100 lines of MongoDB semantics into the fake — $lookup with let, $mergeObjects, $indexOfArray, missing-key-tolerant $group — because the production aggregations need features mongomock does not have.

Redis and Taskiq

Never used. TASKIQ_RUN_INLINE=True swaps the Redis stream broker for Taskiq's InMemoryBroker, so cascaded tasks execute inline, in-process. The broker, the locks, and the pub/sub are never exercised.

Outbound HTTP

No interception library is installed at all — no respx, no responses, no vcrpy. The one HTTP fake monkeypatches a function. Consequence: the Slice Tartlet client, with all its pagination and auth logic, has zero tests.

Test data

No factories.py, no data/ folder, no faker. Two factory fixtures in the root conftest do follow the defaults-plus-overrides pattern. Everything else is inline literals — realistic ones ("Jane Doe", "2022 Share Incentive Plan"), but literals. There are no fixture files on disk at all: PDFs are synthesized blank, in memory.

Time and randomness

No freezegun, no seeded RNG, no clock injection. Determinism is achieved by never depending on time: volatile fields are stripped before comparison. Two real asyncio.sleep calls exist in the TTL-cache tests — the only theoretical flake source in the suite.

How they run

There is no pytest job in CI. The only pull-request check is pre-commit.yml. Tests reach CI indirectly, through a pre-commit hook that loops over three hard-coded directories:

The verdict

This team has built a genuinely excellent test suite — for the 10% of the codebase that cannot hurt them. 219 tests run in 6.4 seconds and every one is deterministic, readable, and fast. But the tests cluster on pure functions, and the risk clusters on I/O, orchestration, HTTP, Mongo aggregations, and LLM accuracy, where the test count is approximately zero. The problem is allocation, not craft.

The engine is pure, deterministic, and cannot touch a customer. The service owns every I/O path, the orchestration, the money, and the match quality that a human will act on.

The target shape — a diamond, not a pyramid

The pure libs are already over-served; the risk is concentrated in the integration seam. Three properties of this system dictate the shape:

  • LLM non-determinism forces a split. Accuracy cannot go in the PR gate — it costs money and it flickers. So you run two things: a deterministic PR check (prompt-file hashes pinned, DTO parsing, the repair loop) and a statistical nightly eval (real providers, labelled documents, precision and recall with a threshold and a trend line). The current suite has the first half and calls it done.
  • Mongo aggregations cannot be faked. $lookup with let, $mergeObjects, $group over missing keys, plus schema validators and unique indexes — the fake models none of it faithfully, and every one is on the customer-facing results path. This single fact pushes the center of gravity from "unit" to "component with a real container."
  • Taskiq orchestration is a state machine over Mongo, not a queue problem. Deferral, supersede, cancellation, heartbeat reaping and maintenance gating are all decided by reading and writing job_items — they don't need Redis. Use the in-memory broker plus real Mongo for the bulk, and spend a real Redis container on only the handful of tests that assert genuine distributed behavior: lock mutual exclusion, stuck-item reaping, and graceful drain on SIGTERM.

And don't add the 104th comparison_engine test. Every marginal hour is worth more in the fat middle.

Where the guide has no answer

The guide was written for deterministic backends. Three of mono-ai's largest risks fall entirely outside it, and it would be dishonest to score them:

  • Extraction accuracy. The product's whole value is: does the LLM pull the right grant_units out of a real board approval? The guide has no concept of a collaborator whose output quality is the feature. The mapping worth making: an eval suite — golden documents, expected extractions, a scored threshold, run nightly rather than per-PR — is the LLM-era analogue of the guide's E2E tier. Its absence is the single largest untested risk in the product, and this framework cannot express it.
  • Prompt regression. No test pins prompt content. A one-word edit can silently degrade extraction across every document type.
  • Cost regression. The cost endpoint reads real spend from Langfuse; nothing guards against a change that doubles token usage. The guide's five exit doors don't include "money".

Top five changes to close the gap

  1. Add a pytest job to CI. Half a day. Today the deploy pipeline ships to staging and production without running a single test, and 60 of 219 tests execute nowhere. Every other item here is worthless until a green suite is a merge requirement.
  2. Write component tests through the HTTP door — the guide's entire thesis. httpx + ASGITransport over the existing mock_environment fixture. This one change lights up sections 1, 3, 4 and half of 6, and it is what AGENTS.md already told the team to do.
  3. Replace mongomock with a real MongoDB container, and install the schema the production way. This deletes a hundred lines of fake-Mongo maintenance and an entire class of "passes in test, fails in prod" aggregation bugs.
  4. Isolate the network properly: add respx plus deny-all-egress, test the Tartlet client, and simulate the timeout and 5xx chaos §5.5 asks for.
  5. Cover the queue and destructive paths with the extra-mile pattern: arrange two jobs, act on one, assert the other survives. Deliver a duplicate task and assert idempotency. Fail a task and assert it lands FAILED and surfaces in error_groups.

Runner-up, outside the guide's world but arguably first for the business: build the eval suite.

Anatomy of the ai-testing skill

The testing doctrine the code actually follows lives in one place: .cursor/skills/ai-testing/. It is not an autonomous agent and it holds no code — it is a progressive-disclosure document bundle: one always-loaded entry file that routes to four on-demand reference docs. Total surface is five markdown files, ~263 lines. Its whole job is to keep an AI (or a human) writing component tests for the ai_documents pipeline in one consistent house style.

There is no agent, and that is the point

The bundle ships no agent.md, no autonomous loop, no tools of its own beyond a declared allowed-tools list (Read, Grep, Glob, Write, StrReplace, Shell). It is instructional context, loaded on demand when a request touches ai_documents tests. The "pieces" below are documents that shape behaviour, not actors that take it.

How the pieces fit together

Piece by piece

01

SKILL.md — the entry point & router

Defines the core unit: "a component test validates one ai_documents pipeline component through its public entry point, with only external edges mocked." It defers Python style to PYTHON_GUIDELINES.md and domain vocabulary (Canonical / Full / Result / ComparisonMatch) to services/ai_documents/AGENTS.md rather than restating them. Its four workflows each name a trigger and route to a reference: choosing a layer → tiers, writing → style then component-tests, reviewing → checklist, mocking config → the "MockSettings, never os.environ" law. It closes with the two run commands (whole suite, or one component).

Contributes: orientation + routingLoaded: always
02

test-tiers.md — where does this test belong?

The gatekeeper. It draws four tiers and, crucially, says which one this skill owns: only component tests (tests/test_<component>/). The other three — use-case / full-job (tests/test_use_cases/, with taskiq, containers, object-storage mocks), API / service integration (FastAPI layer), and pure unit — are explicitly out of scope, and it warns not to copy taskiq / worker / container-patching setup down into component tests. This is the doc that stops a test from being written at the wrong altitude.

Contributes: the scope boundaryRead: first, when jobs/workers/HTTP are mentioned
03

test-style.md — the reusable conventions

The house style, in four parts. Shape: drive the public entry point, never assert private internals; three beats — arrange, act once, assert; name tests test_<subject>_<behavior>; one component per file. Assertions: assert the fields that prove data transfer (identities, transformed values, counts, collection names, persisted rows); prefer assert_matches over whole-object equality; never assert prompt wording or LLM output quality; pin failure paths. Fixtures: reuse before adding, keep single-use local, promote to root conftest.py only after reuse. Determinism: normalize volatile fields, patch with unittest.mock, configure through the settings object — not import order or the environment.

Contributes: naming, arrangement, assertion rulesRead: before writing
04

ai-documents-component-tests.md — the concrete playbook

The longest reference, and the one that turns style into code. Line vs. branch — why both columns matter

Line coverage asks "did this line run at all?" Branch coverage asks "did every if go both ways, did every except fire, did every early-return trigger?" A file can be 90% line-covered and 10% branch-covered when the happy path runs top to bottom but every guard, fallback and error arm is skipped. In this codebase that is the dominant pattern — which is why branch coverage is the honest headline and line coverage flatters.

The one-sentence takeaway

Coverage confirms the report's thesis with numbers: the pure, computational core is branch-tested well (60–73%), while the service's edges — HTTP routes (3.9%), LLM response handling (11.4%), and external-entity integration (1.1%) — are executed on their happy path but almost never forked. The suite proves the arithmetic is right; it does not yet prove the machinery around it behaves when inputs go wrong.

Mutation testing — does the suite actually catch bugs?

Coverage answers "did this line run?" Mutation testing answers the harder question: "if this line were wrong, would a test fail?" mutmut injects one small fault at a time — flip a > to >=, blank a return value, negate a guard — and re-runs the suite. A killed mutant means a test caught the fault; a survivor means the line could ship broken and stay green. Across a sample of 22 files it generated 4,694 mutants, of which the suite killed 1,741 — a 63.9% mutation score on the code it covers, and 37.1% once you count lines no test runs at all.

Two scores, because "covered" flatters

Mutation score (covered) = killed / (killed + survived) — how good the tests are at catching faults in lines they run. Overall also counts "no-tests" mutants (statements the suite never executes) as un-killed. The gap between 63.9% and 37.1% is the same gap tab-wide: decent where the tests reach, nothing where they don't. 1,969 of 4,694 mutants — 42% — are in code no test executes.
