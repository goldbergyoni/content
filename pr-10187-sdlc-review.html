Domain basics, for newcomers

What does "document template matching" even mean, and where does Lexical fit in?

Slice manages employee equity (stock options, RSUs, etc.). Every time something happens to a grant — it's issued, exercised, a share certificate is produced — the platform needs to generate a real legal document (an award letter, an exercise notice, a share certificate). Companies configure reusable document templates for these, and the system must automatically pick the right template for each grant.

That's where template filters come in: a filter is a field on a template (e.g. "which grant types", "which equity plan(s)", "early-exercise allowed?") that narrows when it's allowed to match. The rule is simple but easy to get subtly wrong: an empty filter is a wildcard (matches anything), a filled filter must intersect the grant's actual value. There are also two parallel matching modes — "strict" (evaluates one grant at a time, the default) and "loose" (evaluates a batch of grants together, gated by a feature flag) — and every new filter has to be wired into both code paths or it silently misbehaves for whichever mode wasn't updated. That exact bug shipped once before, in PR #9703 (the "plan filter" / equityPlanIds feature), and is now the running example throughout this PR's docs.

Where "Lexical" comes in: Lexical is Meta's open-source rich-text editor framework; Slice's @slice/lexical-react package wraps it to power the actual text-editing surface used when a company customizes the wording inside a document template (plus paste handling for content copied in from Google Docs / Word). It has no code-level connection to the matching-filter logic above — they only share a skill file because Slice bundled "things related to document templates and the editor" under one skill named after the editor. More on that naming choice in the SDLC review.

What is it about

A documentation-only PR: two new Cursor-agent playbooks, zero application code changes

This PR adds a brand-new .cursor/skills/lexical/ skill (SKILL.md + 4 reference docs) that teaches a future coding agent exactly how to (1) add or change a document-template matching filter across all 4 affected layers without repeating the strict/loose bug, and (2) add a new Lexical editor plugin (paste handler, node transform, or UI overlay) the way the existing ones are built. It also repoints libraries/frontend/lexical-react/AGENTS.md at the new skill instead of the old in-package PASTE.md file, which this PR renames/moves into the skill's references/ folder. Nothing under apps/ or libraries/*/src changes — no behavior, no tests, no risk to production.

Conclusions — what this says about the progressive-disclosure design
  • The matching-filter docs are misfiled, not wasted. Widening the search shows add-filter-playbook.md/matching-engine.md document a real, recurring bug class (4+ "strict matching" regressions, plus the worked example's own regression 3 weeks after shipping) — 48 commits in 90 days outside the 3 tracked folders. The problem isn't that this content is unneeded; it's that nobody would think to open a skill called "lexical" to find it. It belongs in its own skill, scoped to workflow-logic/tartlet/frost-templates.
  • The biggest true gap is consumer-side editor wiring, not anything currently in the skill. Zone 3 (frost's documentsEditor//lexicalInput/, glaze's template-editor pages) is 51 commits in 90 days — on par with the editor library itself (64) — yet has zero mentions across all 4 reference docs. This is the actual highest-leverage domain for a skill literally named "lexical" to cover, and today it's the one piece missing entirely.
  • Within the 3 tracked folders specifically (the narrower first pass), the single biggest real category — replaceable placeholders/merge-field chips, 20% of the last 50 commits — also has no reference doc, alongside DocuSign (10%) and template-data validation (8%). 44% of that narrower slice gets no progressive-disclosure support at all.
  • What the skill does cover, it covers reasonably well. Paste-specific work (Google Docs + Word/DOCX) maps cleanly onto paste-pipeline.md + lexical-react-plugins.md, both detailed, accurate, and well-linked (per the Structure tab) — this is the part of the skill actually earning its tokens.
  • Net recommendation: split into (at least) two skills along the fault line the data shows — one for the matching-filter domain (renamed, scoped to where Zone 2's churn happens), one for the actual Lexical editor (renamed or kept, but expanded to cover Zone 3 consumer wiring and placeholders/DocuSign before adding anything else).
