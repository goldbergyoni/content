From Syntax to Intent: The New SDLC, in Full

Software engineering is living through its largest shift since high-level programming languages — from writing syntax to expressing intent. The numbers make it concrete, not speculative: as of early 2026, 85% of professional developers regularly use AI coding agents, 51% use them daily, and an estimated 41% of all new code is AI-generated. Programming has always been translation — problem to design to machine syntax — and that friction is now collapsing. The developer’s work moves up a level: from typing implementation to specifying what to build and verifying the machine built the right thing.

01 · The SpectrumA continuum, not a binary — and verification is the dividing line

The paper refuses the opposition between “vibe coding” and “agentic engineering.” They are two ends of one continuum, and the axis is not whether you use AI but how much structure, verification, and human judgment surrounds its output. The lineage is precise: in February 2025 Andrej Karpathy coined vibe coding — “fully give in to the vibes… forget that the code even exists” — it went viral, was stretched within months to mean any AI-assisted work, and by early 2026 Karpathy himself added agentic engineering for the disciplined end. Position is set by stakes, not status: a weekend prototype can be pure vibe coding; a payment system cannot.

What separates the ends is verification. Tests check the deterministic parts — this input yields that output — and are checked by code. Evals check the non-deterministic parts — right trajectory, right tools, meets the quality bar — and are checked by labelled datasets, rubrics, and LM judges. Output evaluation inspects the final artifact; trajectory evaluation inspects the full sequence of tool calls and reasoning. Both matter, because the most dangerous failure is a fluent output that quietly skipped its checks, still looks right, and may even pass basic tests. Tests and evals are not just gates — they are the most precise channel for communicating intent, which is why the discipline is to write them before the code.

02 · Context EngineeringThe real skill is the onboarding packet, not the clever prompt

Code quality depends far less on clever prompts than on the quality of the context you provide — the shift from prompt engineering to context engineering. The model is onboarding: you would never hand a new hire a witty one-liner and expect a production PR. Every agent needs the same six kinds of context — instructions, knowledge, memory, examples, tools, guardrails — and designing them deliberately is the practice. The sharper decision is how each reaches the model. Static context (AGENTS.md, CLAUDE.md, GEMINI.md, global memory, persona) is loaded on every call, so you pay those tokens whether the task needs them or not; dynamic context (skills on task-match, tool results, RAG docs, windowed history) is paid for only when used. That boundary is both architectural and financial, and should be versioned like any other config.

The pattern that exploits it is Agent Skills with progressive disclosure, in three tiers: at startup the agent sees only lightweight metadata; on a task match it loads the skill’s full instructions; only when needed does it pull deep reference. Capability and context cost decouple — an agent carries dozens of specialties while paying tokens for only the active one. Skills spread fast because they fix four recurring failures: context rot from overloaded prompts, LLMs’ absence of procedural memory, the overhead of multi-agent setups, and a lack of portability across vendors.

03 · The New SDLCThe cycle compresses dramatically — but unevenly

AI compresses the lifecycle, but — the load-bearing insight — unevenly. Implementation that took weeks now takes hours, while requirements, architecture, and verification stay human-paced, so the slow phases become the new bottleneck and the highest-leverage place for human attention. The data captures the tension: surveys report 25–39% productivity gains, yet a METR study found experienced developers 19% slower on certain tasks — dominated by verifying, debugging, and correcting AI output. AI doesn’t eliminate implementation; it converts it from writing into reviewing, guiding, and verifying. Generation is solved; verification is the new cost center.

Architecture stays the most human-centric phase — trade-offs like consistency-vs-availability or build-vs-buy depend on business context AI can’t grasp — but once a decision is documented, agents scaffold whole apps and enforce conventions. The sleeper unlock is maintenance: legacy code “too risky to touch” because only its authors understood it becomes navigable when an agent reads the codebase, learns its patterns, and modifies it while respecting the architecture. Framework migrations and deprecated-API updates that were too tedious to attempt become tractable — often a larger near-term ROI than greenfield velocity.

04 · The Factory ModelYour output is the system that builds software, not the code

Once implementation collapses to hours, the scarce work moves up a level: your primary output is no longer code but the system that produces code. The developer is a factory manager who designs the assembly line and owns quality control rather than hand-assembling each widget. That system has five interlocking components: specifications and context that say what; agents that build; tests and quality gates that verify; feedback loops that correct by routing failures back; guardrails that contain. They form a closed loop, not a checklist — tests without a feedback loop are mere inspection; the loop is what makes the factory self-correcting.

The operating principle is to give agents success criteria, not step-by-step instructions, then let them iterate. Scripting every step caps throughput at your typing speed and reduces the agent to a transcription engine; specifying what “correct” looks like — a precise spec plus a test-and-eval suite — turns it into a loop that converges on a passing state. Economically this is upfront CapEx (schemas, tests, context) that drives down the marginal cost of every later feature. Which raises the obvious question: if the developer is the manager, what is the machine on the floor?

05 · Harness EngineeringAgent = Model + Harness — and the harness is yours, not the provider’s

The model is only the raw engine; an engine can’t build a car without belts, gears, sensors, and an assembly line. That machinery is the harness, six components your team owns and versions: instructions and rule files; tools (functions, MCP servers, APIs); sandboxes and execution environments; orchestration logic (sub-agent spawning, model routing, hand-offs); guardrails and hooks (deterministic code before a tool call, after a file edit, before a commit); and observability (traces, cost and latency metering, drift detection). Its most important product is a closed think → act → observe loop: the model writes a function, orchestration runs it against tests in a sandbox, captures failures, and routes them back — the difference between an agent that finishes and one that flails.

The evidence that this is where leverage lives is striking, holding the model fixed. On Terminal Bench 2.0, one team moved a coding agent from outside the Top 30 to the Top 5 by changing only the harness. A separate LangChain study lifted an agent’s score on the same benchmark by 13.7 points by adjusting only the system prompt, tools, and middleware around a fixed model. The everyday rule of thumb: when an agent misbehaves, the instinct is to blame the model, but the failure usually traces to a missing tool, a vague rule, an absent guardrail, or a context window stuffed with noise.

06 · Roles & the 80% ProblemConductor, orchestrator, and the dangerous last fifth

The developer’s role splits into two postures engineers move between fluidly in a day. In conductor mode they work in real time with an AI pair-programmer, steering each change — right for complex logic, tricky debugging, and unfamiliar code (Copilot, Gemini Code Assist, Cursor, Windsurf), but the human can become the throughput bottleneck. In orchestrator mode they define goals, hand them to agents running in the background and in parallel, and review results (Google Jules, Copilot agent mode, Cursor background agents, Claude Code). Orchestration demands a different skill set — specification, decomposition, evaluation, and system design — and those four, not syntax fluency, are the new core competency.

Underneath both sits the 80% problem: agents rapidly generate ~80% of a feature, but the remaining 20% demands contextual knowledge models lack — and it is the hardest part: edge cases never considered, error handling for realistic failures, integration points, and subtle correctness depending on un-inferable intent. It’s dangerous because the nature of AI errors changed — from syntax mistakes a compiler catches instantly to insidious conceptual failures: wrong business-logic assumptions, unasked clarifying questions, architectural choices that quietly accrue maintenance debt. These survive compilation, basic tests, and a casual glance because the code looks right. Review can no longer be a syntax pass; it must be a correctness-and-intent pass aimed at the hard fifth. Speed comes from allocating attention there — not from accepting more output.

07 · Agents in PracticeFrom prototype to production agent — without a rewrite

Coding agents show up in three places, used by task rather than by rank. In the editor: inline completion and in-place chat, staying in flow (Copilot, Cursor, Windsurf, JetBrains AI Assistant). In the terminal: a plain-language goal handed to an agent with full filesystem access that makes multi-file edits, runs tools and tests, and iterates — where serious vibe coding happens today (Claude Code, Codex CLI, Antigravity CLI, OpenCode, Cline). In the background: an autonomous agent in a cloud sandbox that works for hours and returns a pull request (Google Jules, Copilot agent mode, Cursor background agents, AlphaEvolve).

The bigger shift: the same terminal workflow now reaches production agents — support bots, research assistants, compliance monitors — which need their own memory, scoped permissions, evals, and observability. Google’s Agents CLI packages this: a one-time uvx google-agents-cli setup gives whichever coding agent you use seven new skills across the full ADK lifecycle — scaffold, write, evaluate, deploy to Agent Runtime, wire up observability — so a laptop prototype becomes a production agent without a rewrite. Many agents coordinate on open standards: shared session state, MCP for tool access, A2A for cross-agent delegation. The signal of where this leads: an Anthropic team had agent teams build a working C compiler in Rust over two weeks — humans setting direction and reviewing, not writing the implementation. The bottleneck moved from writing code to specifying and verifying it.

08 · EconomicsThe CapEx/OpEx flip and the token economy

For leaders, velocity is the wrong metric; Total Cost of Ownership is the right one, and it turns on how a workflow splits CapEx (upfront build) against OpEx (run, fix, maintain) — with OpEx now dictated by the token economy, since every interaction is metered per token. Vibe coding looks free (a subscription plus prompts) but hides a compounding bill on three axes: a high token burn rate from dumping unstructured files into context and re-prompting to fix unverified output; a maintenance tax of days spent reverse-engineering AI “spaghetti”; and security remediation that is exponentially costlier in production than at design time. Agentic engineering flips the shape — high CapEx (API schemas, deterministic tests, structured context) for a low, declining marginal cost per feature.

Two levers drive OpEx down. Context engineering is a financial strategy: passing a 100,000-token repository into every prompt is unviable at scale, whereas a dense, high-signal AGENTS.md raises first-pass success — and first-pass success is what kills the expensive re-prompting loop. Intelligent model routing reserves large, advanced models for complex work (requirements, architecture, initial implementation) and routes deterministic tasks (test generation, code review, CI/CD monitoring) to small, fast, cheap models. Funneling every interaction through one frontier model — paying premium prices to fix a typo — is the vibe-coding tax made literal.

09 · Adoption & PrinciplesWhere to start, and what will outlast the tools

None of this is a future state; it is the work in front of us, and one principle holds at every scale: AI amplifies the engineering culture it lands in. Strong tests, clear architecture, and healthy review become a force multiplier; their absence multiplies just as fast. For an individual: start a ten-line AGENTS.md (stack, conventions, hard rules, workflow — add a rule each time the agent misbehaves), turn one repetitive workflow into a first end-to-end agent, write tests and evals before code, and review every line that ships. For a leader: treat context as code — versioned, reviewed in PRs, owned by named engineers — and set the bar at a passing eval suite, not a one-off demo. For an organization: invest in the production substrate (trajectory and final-response evals in CI, traces, scoped permissions) and open standards before scale, and reframe hiring around judgment, not raw implementation.

Three principles, the authors expect, outlast any specific tool: structure scales, vibes don’t; AI amplifies your engineering culture; the human role is evolving, not diminishing. The skills that matter shift from implementation toward judgment — architecture, precise specification, critical evaluation, and the design of constraints and feedback loops. 4. The Factory Model

  • Output reframe: the developer's primary deliverable is no longer code — it's the system that produces code. Code becomes the line's output; the line itself is the work.
  • Five components of that system: (1) specifications & context that define what to build, (2) agents that translate specs into implementation, (3) tests & quality gates that verify correctness, (4) feedback loops that route failures back to agents for correction, (5) guardrails that constrain agents to safe, predictable behavior. They form a closed, self-correcting loop, not a checklist.
  • Success criteria, not step-by-step instructions: give agents a precise spec plus tests/evals (the "contract" with the AI), then let them iterate to a passing state. This is the structural divide between agentic engineering and vibe coding.
  • Factory-manager analogy: a manager designs the assembly line and owns quality control rather than assembling each widget; the developer designs the development system and ensures its output meets the bar. Upstream design over downstream inspection — and upfront CapEx that lowers the marginal cost of every feature.
  • The model is just the raw engine: if the developer is the factory manager, the AI model is merely the engine on the floor — it needs belts, gears, sensors, and the assembly line around it. That surrounding machinery is the harness, which is exactly what the next section (Harness Engineering) dissects.

6. Developer Roles + The 80% Problem

  • Conductor/orchestrator is a duality, not a hierarchy. Developers move fluidly between hands-on real-time direction in the IDE (conductor) and higher-abstraction async delegation to parallel background agents (orchestrator), choosing the posture by task stakes and codebase familiarity rather than by which is "more advanced."
  • Conductor's main risk is throughput; orchestrator's is specification/review quality. A conductor who gates every keystroke caps the productivity gain from AI; an orchestrator who under-specifies or under-reviews gets bad output produced fast and in parallel.
  • The orchestrator runs on a different skill set. Not syntax fluency but four skills: Specification (unambiguous tasks), Decomposition (right-sized units), Evaluation (fast quality judgment), and System design (constraints, tests, feedback loops).
  • The 80% problem caps delegation. Agents generate ~80% of a feature rapidly, but the remaining 20% — edge cases, error handling, integration points, subtle correctness — needs deep contextual knowledge models lack. The leftover is the hardest, highest-consequence part, not evenly distributed grunt work.
  • AI errors evolved from syntax to insidious conceptual failures. Wrong business-logic assumptions, not asking for clarification on ambiguity, missing edge cases, and architecture that creates long-term maintenance burden — failures that survive compilation and basic tests because the code "looks right."
  • Because the failure class changed, review must change. Syntax-level checks are obsolete as the safety net; review has to target correctness and intent on the hard 20%.
  • The effective posture is focused allocation, not blanket acceptance. Use AI for rapid implementation of well-specified tasks; reserve scarce human attention for ambiguity, architectural trade-offs, and correctness verification. Be faster by focusing expertise where it matters, not by accepting everything.
  • The four orchestrator skills are also the antidote to the 80% problem. Precise specs and strong evals are how you surface the hard 20% early instead of discovering it in production.

The bottleneck moved from writing code to specifying what it should do and verifying the agents did it — the section's load-bearing proof point.

8. The Economics of AI Development

  • Reframe the metric from velocity to TCO. Leaders should evaluate AI workflows by Total Cost of Ownership, decomposed into CapEx (upfront build) vs OpEx (ongoing run/fix/maintain) — and in the AI era OpEx is heavily dictated by the token economy, since every LLM interaction is metered per input and output token.
  • Vibe coding = low CapEx, high OpEx (hidden debt). Near-zero barrier (a subscription plus casual prompts) masks a compounding operational burden: (1) token burn rate from dumping unstructured files into context and re-prompting the model to fix its own unverified mistakes at low first-pass success; (2) a maintenance tax as engineers later spend days reverse-engineering AI "spaghetti"; (3) security remediation, where no eval harness means rapid vulnerability generation and exponentially costlier production fixes.
  • Agentic engineering = high CapEx, low OpEx (the flip). A deliberate upfront investment — API schemas, deterministic test suites, and structured agent context — drops the marginal cost of shipping and maintaining each feature, because output from the governed "factory" is structurally sound, pre-tested, and standards-aligned.
  • Context engineering is a financial lever, not just a technical skill. LLMs charge per token, so passing a 100k-token repo into every prompt is financially unviable at scale; a dense, high-signal payload (a precise AGENTS.md plus guardrails) raises first-pass success and avoids the costly trial-and-error loops that define vibe coding.
  • Scale efficiency with dynamic context. Advanced agentic engineering loads knowledge on demand via skills and tool calling (e.g., MCP servers, per the Day-3 paper), so the agent pays token cost only for what a task actually needs.
  • Intelligent model routing across a multi-model ecosystem. Vibe coding pays frontier-model premium prices even to fix a typo; a well-designed factory routes complex tasks (requirements, architecture, initial implementation) to large advanced models and deterministic low-complexity tasks (test generation, code review, CI/CD monitoring) to smaller/faster/cheaper models — maintaining quality while systematically driving down token cost.

9. Adoption & Durable Principles

  • "AI amplifies the engineering culture it lands in." This is the unifying principle across all three audiences. The same agent multiplies a disciplined team's strengths and an undisciplined team's weaknesses — tooling does not substitute for culture.
  • "Set the bar at the eval, not the demo." A demo proves success once; a passing eval suite proves reliability. But an eval without a rubric measures nothing — score task success, tool-use quality, trajectory compliance, hallucination, and response quality, and gate shipping on coverage the way test coverage gates a deployment.
  • Treat harness artifacts as code. AGENTS.md, system prompts, eval suites, skill libraries, and MCP connections should be reviewed in PRs, versioned, and owned by named engineers. Built once and refined many times, they become a compounding shared team asset; left unmanaged, the harness drifts and behavior becomes irreproducible.
  • Plan for hybrid human-plus-agent teams. Agents are now participants, not just tools. Humans set direction, agents implement, and explicit handoff protocols govern the boundary — so code review, on-call rotations, and team structures all have to evolve.
  • Reframe hiring around judgment, not implementation. As implementation cheapens, the bottleneck moves to specification, evaluation, architectural judgment, and review. The most valuable engineers direct agents well rather than writing the most code.
  • The three durable principles: (1) Structure scales, vibes don't — production work needs specs, tests, guardrails, and human oversight of architecture; (2) AI amplifies your engineering culture — a force multiplier of both strengths and weaknesses; (3) The human role is evolving, not diminishing — skills shift from implementation to judgment.
  • Build the production substrate before scale, not after. CI evals (trajectory and final-response), traces of every run, scoped per-agent permissions, and generated-code-aware security review must exist before the first production agent ships. Adopt open standards (MCP, A2A) now to preserve vendor optionality.
  • The closing thesis: "Generation is solved. Verification, judgment, and direction are the new craft." Paired with the framing of intent as the new interface, this reframes the engineer's value away from producing code toward directing and verifying the systems that produce it.

The Vibe Coding → Agentic Engineering Spectrum

The paper's foundational move is to reject the binary. "Vibe coding" and "agentic engineering" are not two camps but the endpoints of one continuum, and the axis that separates them is not whether you use AI — it's how much structure, verification, and human judgment surrounds the AI's output. For a senior engineer the load-bearing claim is precise and uncomfortable: without both tests and evals, the practice is always vibe coding regardless of how sophisticated the prompts are.

From syntax to intent — and why the term fractured

The deeper shift the paper names is from writing code to expressing intent. Programming has historically been an act of translation (problem → abstract design → machine syntax), and each step adds friction. That friction is now collapsing. The adoption data backs the framing rather than a forecast: as of early 2026, 85% of professional developers regularly use AI coding agents, 51% use them daily, and an estimated 41% of all new code is AI-generated.

The terminology has a precise lineage worth keeping straight:

  • February 2025 — Andrej Karpathy coins vibe coding: "fully give in to the vibes, embrace exponentials, and forget that the code even exists." Describe in natural language, accept the output, paste errors back when something breaks. It went viral because it named what many were already doing.
  • The dilution problem — within months "vibe coding" was applied to any AI-assisted workflow, including a senior engineer implementing a well-specified feature. Applied that broadly, the term lost meaning.
  • Early 2026 — Karpathy himself concedes the original framing was too narrow and introduces agentic engineering for the disciplined end of the spectrum.

The stakes are framed bluntly: telling a CTO your team is vibe coding the payment processing system should raise alarms; saying you practice agentic engineering — AI implementing under human-designed constraints with test coverage ensuring correctness — is a fundamentally different conversation. Same tools, different discipline.

Verification: the single biggest differentiator

The paper is explicit that how outputs get verified is what most distinguishes the ends of the spectrum. In vibe coding, verification is optional — run it, eyeball it. In agentic engineering, two mechanisms work together, and they check different kinds of things:

  • Tests verify the deterministic parts: a function given this input produces that output. They are checked by code.
  • Evals verify the non-deterministic parts: did the agent take the right trajectory of steps, choose the right tools, and produce a final response that meets the quality bar. They are checked by labelled datasets, scoring rubrics, and LM judges.

Both are necessary — a fluent output that skipped its verification steps is a more dangerous failure than one with a visible error, because it "looks right" and may even pass basic tests.

A second-order insight: tests and evals are not just gates, they are the primary mechanism for communicating intent. A well-written eval suite tells the AI what "correct" means and gives an automated way to verify it — more precisely than any natural-language prompt. This is why the recommended posture is to write tests and evals before generating the code.

Why this matters / advanced takeaways

  • The dividing line is verification, not tooling. The same coding agent can be used to vibe code or to do agentic engineering. Sophistication of prompts is irrelevant: without both tests and evals, the practice is always vibe coding. This is the section's hardest, most quotable claim.
  • Trajectory beats output as a failure detector. A confident, well-formed answer that quietly skipped its checks is more dangerous than a visibly broken one. Evals exist precisely because output inspection misses this class of failure.
  • Evals encode intent better than prompts. Treating the eval suite as the contract reframes "prompt engineering" as a weaker substitute for a specification that is itself executable and checkable.
  • Stakes set position. There is no virtue in always being at the agentic end — the skill is calibrating structure to risk, per task, not maximizing autonomy.

Context Engineering — the real skill

The paper's central claim about working with AI is deceptively simple: the quality of AI-generated code depends far less on the cleverness of your prompts than on the quality of the context you provide. This is the shift from prompt engineering (wordsmithing a single instruction to coax good output) to context engineering (architecting the structured information an agent needs to do real work). The reframe at the heart of the section is worth holding onto: stop asking "how do I trick the AI into writing good code?" and start asking "what would a new team member need to know to contribute effectively, and how do I encode that in a form the AI can use?"

For a senior engineer, the useful mental model is onboarding. You would never hand a new hire a clever one-liner and expect a production PR. You would give them the codebase conventions, the architecture, the domain rules, examples of good work, the tools they're allowed to touch, and the lines they must not cross. Context engineering is that onboarding packet — made machine-consumable, versioned, and reviewed like any other configuration.

The six types of context

Every agent needs the same six categories of context. Designing them deliberately is the practice.

Knowledge Retrieved documents and domain-specific data Architectural diagrams, design docs, domain reference data
Memory Short-term session state plus long-term persistent state Session logs of what just happened; persistent record of what the project is

Static vs. dynamic context: an architectural AND economic trade-off

The real engineering decision is not whether to provide these six types, but how each one reaches the model: loaded upfront on every call, or retrieved on demand. This splits context into two classes with very different cost profiles.

Static context is always loaded. It defines who the agent is and how it behaves: system instructions, rule files (AGENTS.md, CLAUDE.md, GEMINI.md), global memory, and persona definitions. Because every token is present in every interaction regardless of relevance, static context is expensive — you pay for it on each call whether the current task needs it or not.

Dynamic context is loaded on demand. Skill instructions triggered by task matching, tool results retrieved during execution, documents fetched from RAG pipelines, and windowed session history. It is efficient precisely because the agent pays the token cost only when the information is actually needed.

The boundary between the two is a genuine trade-off, not a default:

  • Too much static context wastes tokens on every call and dilutes the signal the model is trying to attend to.
  • Too little static context means the agent forgets critical rules that should always apply.

The paper's prescription: treat this boundary as a first-class architectural decision — reviewed and versioned like any other configuration. It is also a financial lever. In the token economy, every byte you send is billed on every request, so deciding what is "always on" versus "fetched when relevant" directly shapes operational cost at scale.

Agent Skills: progressive disclosure as the key pattern

The most powerful pattern for managing dynamic context is Agent Skills — structured, portable packages of procedural knowledge the agent loads only when the task calls for it. Rather than embedding every specialized capability into the system prompt (which would balloon static context), Skills let the agent stay a lightweight generalist that flexes into specialist roles on demand.

The mechanism is progressive disclosure, staged in three tiers:

  1. At startup, the agent sees only lightweight metadata for each skill — enough to know it exists and what it's for.
  2. When a task matches, the agent loads that skill's full instructions.
  3. Only when explicitly needed, it pulls deep reference material.

The payoff: an agent can carry dozens of specialized capabilities while paying the token cost for only the one it is actively using.

The four problems Skills solve

The paper attributes the rapid adoption of Agent Skills across major coding agents and enterprise platforms to four specific, recurring failures they address:

  • Context rot from overloaded prompts — stuffing everything into static context degrades the model's attention and signal.
  • Absence of procedural memory for LLMs — models have no native place to retain reusable, step-by-step know-how across tasks.
  • Operational overhead of multi-agent architectures — Skills package capability without spinning up and coordinating separate agents.
  • Lack of portability across tools and vendors — a skill is a portable package, not glue code bonded to one harness.

Why this matters / advanced takeaways

  • The static/dynamic split is a cost model, not just an architecture diagram. Static tokens are a fixed tax on every single call. Audit what truly belongs in AGENTS.md/CLAUDE.md/GEMINI.md versus what can be a skill — the boundary is where your per-interaction token bill is decided.
  • Progressive disclosure breaks the "more capability = bigger prompt" coupling. You can carry dozens of specialist skills while only paying for the active one, so capability and context cost scale independently.
  • Skills give LLMs the procedural memory they structurally lack. This is the difference between an agent that re-derives a workflow each time and one that reliably executes an encoded procedure — and it's portable across vendors.
  • Treat context as code. The paper is explicit that the static/dynamic boundary should be reviewed and versioned. Rule files, skills, and persona definitions are configuration that drifts if unowned.
  • The onboarding reframe is the durable lesson. "What would a skilled new teammate need to know?" generalizes past any specific tool. If the answer is "always," it's static; if it's "for this kind of task," it's a skill; if it's "occasionally," it's RAG or a tool call.
  • Context engineering is the bridge. It is what separates disciplined agentic engineering from ad-hoc vibe coding — the same model behaves very differently depending on the context architecture around it.

The New SDLC, Phase by Phase

The SDLC has already survived one revolution. Over the past two decades most enterprises traded sequential waterfall for iterative models — Agile sprints, CI, DevOps pipelines, continuous release. AI compresses the cycle dramatically but unevenly. Implementation that once took weeks now takes hours, while requirements, architecture, and verification remain stubbornly human-paced. The result is not a faster version of the old SDLC — it is a different workflow, where phase boundaries blur, iteration shrinks from weeks to minutes, and the developer's center of gravity moves from primary implementor to system designer and quality arbiter. The bottleneck is no longer human hands typing boilerplate; it is human minds defining the boundaries.

Requirements and planning

Requirements is where the gap between intent and implementation has historically been widest: translating business needs into specs is manual and error-prone, leaving a persistent gap between what stakeholders want and what engineers build.

AI now participates directly in refinement — generating user stories from briefs, surfacing edge cases humans miss, producing API schemas from natural language, and turning specs into interactive prototypes in minutes. The deepest change is structural: specification and initial implementation are produced simultaneously. Requirements stop being a document handed off between teams and become a conversation between humans and AI, collapsing the requirements-to-prototype loop toward zero.

Design and architecture

Architecture remains the most stubbornly human-centric phase, and for good reason. Architectural decisions are fundamentally about trade-offs — consistency vs. availability, complexity vs. flexibility, build vs. buy — and those trade-offs depend on business context, organizational constraints, and long-term strategy that AI cannot fully grasp.

What AI does excel at is implementing architectural decisions once they are made. Given a clear architecture document, agents scaffold whole applications, generate consistent patterns across modules, and conform new code to established conventions. The developer's role shifts from writing the boilerplate to making and documenting the structural decisions the boilerplate implements.

Implementation

Coding agents generate entire features from natural-language descriptions, implement complex algorithms, and produce coherent multi-file changes. The productivity gains are real: industry surveys report 25 to 39% productivity improvements, with some tasks seeing larger gains.

But the headline numbers hide nuance. A METR study found experienced developers using AI assistants actually took 19% longer on certain tasks — largely from the time spent verifying, debugging, and correcting AI output. The lesson is not that AI is slower; it is that AI transforms implementation rather than eliminating it. The work shifts from writing to reviewing, guiding, and verifying.

Testing and quality assurance

Testing AI-generated code means evaluating not just what the agent produced but how it got there:

  • Output evaluation checks the final artifact: does it compile, do the tests pass?
  • Trajectory evaluation checks the full sequence of tool calls and intermediate reasoning.

Both are necessary, because a fluent output that skipped its verification steps is a more dangerous failure than one with a visible error. Beyond detection, AI also transforms test generation — producing edge cases and property-based tests humans miss. Most importantly, tests and evals become the primary mechanism for communicating intent to agents: a well-written eval suite tells the AI what "correct" means and gives an automated way to verify it.

Code review and deployment

Review is being augmented, not replaced. AI acts as a first-pass reviewer, flagging potential bugs, style violations, security vulnerabilities, and performance issues before a human sees the code. This does not replace human review — context-dependent calls on design, maintainability, and strategic alignment still need human judgment — but it sharply reduces reviewer cognitive load.

Deployment pipelines are becoming AI-aware: agents monitor deployment health, automatically roll back problematic releases, and predict deployment risk from the nature and scope of changes. Modern platforms increasingly wire AI-powered observability into feedback loops between production behavior and development decisions. Maintenance and evolution

Perhaps the most underestimated transformation. Legacy codebases that were once impenetrable to new team members can now be navigated, understood, and modified with AI assistance: an agent reads the codebase, learns its patterns, identifies the files relevant to a change, and implements modifications while respecting the existing architecture.

The implications for technical debt are large. Code that was "too risky to touch" because only its original authors understood it can now be safely refactored, modernized, and extended. Agents can systematically migrate codebases between frameworks, update deprecated APIs, and modernize test suites — tasks that were previously so tedious and risky that they simply never happened.

The Factory Model — Building the System That Builds Software

The factory model is the mental model that ties together every transformation the paper has described so far. Its single load-bearing claim is a reframe of what a developer actually produces: your primary output is no longer code — it's the system that produces code. Once implementation collapses from weeks to hours, the scarce, high-leverage work moves up a level. You stop hand-assembling the artifact and start designing the line that assembles it for you.

This section unpacks the five components of that system, the factory-manager analogy that anchors it, the operating principle that makes it work (success criteria, not step-by-step instructions), and the question it leaves open — which sets up Harness Engineering.

The reframe: output is the system

For most of computing history the deliverable was the code. In the factory model, the code is the line's output; the developer's deliverable is the line itself — the specifications, agents, tests, feedback loops, and guardrails that, taken together, reliably turn intent into working software. A senior engineer is no longer measured by lines written but by whether the system they designed produces software that meets the required standard.

The five components of the system

The paper defines the code-producing system as five interlocking parts. Note the flow embedded in them: specs say what, agents build, tests verify, feedback loops correct, and guardrails contain.

Component Role Example artifacts
Specifications & context Define what needs to be built and the conditions it must satisfy Formal specs, architecture docs, AGENTS.md/CLAUDE.md/GEMINI.md, memory files, API schemas
Agents Translate specifications into implementation Terminal and background coding agents, sub-agents, multi-agent workflows
Tests & quality gates Verify that the output is correct Deterministic test suites, eval suites with rubrics, CI/CD gates, LM judges
Feedback loops Route failures back to agents for correction Captured test/error output fed back to the agent, regression suites, the continuous quality flywheel
Guardrails Constrain agents to safe, predictable behavior Hard constraints, hooks at lifecycle points, formatting and safety validations

The factory-manager analogy

A factory manager does not assemble every widget by hand. They design the assembly line and own quality control. The modern developer designs the development system and ensures its output meets the bar. The work is upstream of any individual artifact: get the line right, and every widget that comes off it is correct by construction rather than by inspection. The corollary is economic — this is upfront CapEx (designing schemas, tests, and context) that drives down the marginal cost of every feature the line subsequently ships.

The operating principle: success criteria, not step-by-step instructions

The principle that makes the line run is this: give agents success criteria, then let them iterate — do not script every step. A precise spec plus a test-and-eval suite tells the agent what correct means and gives it an automated way to check itself. That turns the agent into a closed loop that converges on a passing state, instead of a transcription engine waiting on the next instruction. It is also why tests and evals are framed as the contract with the AI: they communicate intent more precisely than any prose prompt, and they are what separates agentic engineering from vibe coding.

The handoff to Harness Engineering

The factory model raises the obvious next question: what is the central machine on the floor? If the developer is the factory manager, the AI model is merely the raw engine — and an engine alone cannot manufacture a car. It needs belts, gears, safety sensors, and the assembly line around it. In AI-assisted development, that surrounding machinery is the harness. The factory model tells you the developer's job is to design the system; Harness Engineering tells you what that system is actually made of.

Why this matters / advanced takeaways

  • Your output is the system, not the code. Optimize the line, not the widget. Reviewing the system that produces a thousand changes is higher leverage than reviewing any one change — and it is where senior judgment now compounds.
  • Success criteria beat step-by-step instructions. Scripting steps reduces an agent to a transcription engine and caps throughput at your typing speed. Specifying what correct looks like — via tests, evals, and rubrics — lets the agent iterate to a passing state on its own. This is the structural difference between agentic engineering and vibe coding.
  • The five components are a closed loop, not a checklist. Specs, agents, tests, feedback, and guardrails only deliver reliability when wired together so failures route back automatically. Tests without a feedback loop are inspection; the loop is what makes the factory self-correcting.
  • The model is just the engine. Treating a model upgrade as the fix for agent failures is the wrong investment. The factory model deliberately separates the engine (model) from the machinery (harness) — which is precisely the subject of the next section.

Harness Engineering: What Surrounds the Model

When engineers first start building with AI agents, there is a strong temptation to treat the model as the system. A new model ships and the agent gets smarter; an older model and it gets worse. The model becomes the explanation for everything good and bad.

That intuition is wrong, and it leads to the wrong investments. The model is one input into a running agent. Everything else — the prompts, the tools, the context policies, the hooks, the sandboxes, the sub-agents, the observability — is the harness: the scaffolding wrapped around the model that lets it actually finish something.

The equation

Agent = Model + Harness

A raw model is not an agent. It becomes one once a harness gives it state, tool execution, feedback loops, and enforceable constraints. The behaviour you experience working with Claude Code, Cursor, Codex, Antigravity, Aider, or Cline is dominated by what the harness does — not just by which model is underneath. To borrow the whitepaper's image: if the developer is the factory manager, the model is the raw engine on the factory floor. An engine alone cannot manufacture a car; it needs belts, gears, safety sensors, and an assembly line. The harness is that surrounding machinery.

What's in the harness

A harness is built from six components. Crucially, this is the team's surface area, not the model provider's — it is what you own, configure, and version.

Component What it includes Why it matters
1. Instructions & Rule Files The text defining who the agent is, what it cares about, and what it is forbidden from doing: AGENTS.md, CLAUDE.md, GEMINI.md, skill files, and sub-agent prompts. Sets the agent's role, goals, and hard boundaries before it acts. A vague rule here surfaces later as misbehaviour everywhere.
2. Tools The functions, MCP servers, and APIs the agent can call — plus the prose around them telling the model when and how to call them. Connects the model to the world. A missing tool or unclear calling instructions is a common, silent cause of failure.
3. Sandboxes & Execution Environments Where the agent's code actually runs, what it can access, and what it cannot reach. Keeps the agent secure and contained while it executes real code, reads files, and runs tests.
4. Orchestration Logic Sub-agent spawning, model routing, hand-offs between specialists, and the rules that govern when each one fires. Runs the loop and the feedback cycle — it is what captures a result and decides whether to continue, retry, or delegate.
5. Guardrails / Hooks Deterministic code that runs at specific lifecycle points: before a tool call, after a file edit, before a commit. The place for the things the agent should never forget but often does. Non-probabilistic enforcement at the moments that matter.
6. Observability Logs, traces, evaluations, cost and latency metering, drift detection. Without it there is no way to tell whether the agent is doing well or quietly drifting.

Vibe coding vs agentic engineering: a harness distinction

The transition from vibe coding to agentic engineering is not about which tool you use — a developer can do either with the exact same agent. It is defined by how deliberately you configure and apply the harness. Vibe coding relies on minimal or implicit scaffolding aimed purely at rapid implementation. Agentic engineering relies on clear, extensive harness abstractions that guide the AI from the first planning document all the way through to production monitoring.

Why this matters — advanced takeaways

The harness effect is large and measurable, with the model held fixed.

  • On Terminal Bench 2.0, one team moved a coding agent from outside the Top 30 to the Top 5 by changing only the harness — no model change at all.
  • A separate study at LangChain raised a coding agent's score on the same benchmark by 13.7 points by tweaking only the system prompt, tools, and middleware around a fixed model.

The everyday version of this is the most useful rule of thumb a team can adopt: when an agent does something wrong, the first instinct is to blame the model. More often, the failure traces back to a missing tool, a vague rule, an absent guardrail, or a context window stuffed with noise.

Most agent failures, examined honestly, are configuration failures.

The practical implication for senior engineers: invest where the leverage is. The harness is your surface area to design, version, and improve — and it is where the measurable wins live. Treat the six components as first-class engineering artifacts, not afterthoughts bolted onto whichever frontier model happens to be current.

The Developer's Evolving Role + The 80% Problem

As AI absorbs more of the implementation work, the developer's job is not shrinking so much as bifurcating. The whitepaper frames this through two modes that engineers move between fluidly over the course of a single day: the conductor and the orchestrator. Neither is a permanent identity or a rung on a ladder; they are postures matched to the task at hand. Running underneath both is a hard ceiling on what delegation buys you — the 80% problem — and a quiet shift in the kind of mistakes AI makes, from syntax errors you can spot to conceptual errors you can't.

Two modes of working with agents

Conductor: hands-on, real-time direction

In conductor mode, the developer works in real time with an AI pair-programmer. They are in the IDE, watching code appear, steering with prompts and corrections, and keeping fine-grained control over what gets written. The AI is a powerful instrument, but the developer is actively directing every movement.

This mode fits complex logic, tricky debugging, and unfamiliar codebases — anywhere the developer needs to understand each change as it lands. Tools like GitHub Copilot, Gemini Code Assist, Cursor, and Windsurf support it through inline completions, chat, and edit-in-place. It is the natural mode for engineers from traditional backgrounds, because it preserves the sense of understanding and control they value.

The risk is throughput: if a human is personally directing every keystroke, the productivity gain from AI is capped. The conductor can become the bottleneck.

Orchestrator: async, multi-agent delegation

In orchestrator mode, the developer operates at a higher level of abstraction. They define goals, assign them to agents, and review results — but they are not watching code appear line by line. Agents may run in the background, in parallel, across different parts of the codebase. The developer checks in periodically, reviews output, and provides course corrections.

This mode fits well-defined work: bug fixes, feature implementations against established patterns, codebase migrations, and test generation. Tools like Google Jules, GitHub Copilot agent mode, Cursor background agents, and Claude Code support it through async task execution, often in sandboxed environments with full access to the repo, build tools, and test suites.

Critically, the orchestrator demands a different skill set — not deep fluency in syntax and language idioms, but four capabilities:

  • Specification — defining tasks precisely enough that an agent can execute without ambiguity.
  • Decomposition — breaking large tasks into appropriately sized units for agent execution.
  • Evaluation — quickly assessing whether agent output meets the quality bar.
  • System design — designing the constraints, tests, and feedback loops that keep agents productive.

The nature of AI errors has changed

The 80% problem is dangerous because of how the missing 20% fails. The nature of AI errors has evolved from simple syntax mistakes — which a compiler catches instantly — to insidious conceptual failures:

  • Wrong assumptions about business logic.
  • Failure to seek clarification on ambiguous requirements.
  • Missing edge cases.
  • Architectural decisions that create subtle, long-term maintenance burdens.

These are harder to detect precisely because the code "looks right" and may even pass basic tests. The error is not in the grammar; it is in the understanding.

The effective posture

The developers who navigate this best adopt a deliberate division of labor. They use AI for what it's good at — rapid implementation of well-specified tasks — while reserving their own attention for what AI struggles with: ambiguous requirements, architectural trade-offs, and correctness verification.

The key distinction: they do not try to be faster by accepting everything the AI produces. They try to be faster by focusing their expertise where it matters most.

Why this matters / advanced takeaways

  • The error class shifted, so the review discipline must shift with it. When AI mostly made syntax errors, the toolchain caught them. Now the dangerous failures are conceptual — wrong business-logic assumptions, unasked clarifying questions, missing edge cases, costly architectural choices — and they survive compilation, basic tests, and a casual glance. Review can no longer be a syntax pass; it has to be a correctness and intent pass aimed squarely at the 20%.
  • Conductor and orchestrator are postures, not tiers. The skill is moving between them by stakes and familiarity: conduct the parts you must understand as they're written; orchestrate the well-specified parts you can hand off. Treating orchestration as strictly "more advanced" misses the point — and over-conducting turns the human into the throughput bottleneck.
  • Speed comes from allocation, not acceptance. The leverage is not in trusting more output; it is in concentrating scarce human attention on ambiguity, architectural trade-offs, and verification — the exact places models are weakest. Faster because expertise is focused, not because review was skipped.
  • The orchestrator's four skills are the new core competency. Specification, decomposition, evaluation, and system design displace raw syntax fluency as the differentiating skills — and they are the same skills that contain the 80% problem, since precise specs and good evals are how you force the hard 20% into view early.

The Economics of AI Development

Discussions of AI's impact on the SDLC usually open and close with developer velocity: how fast can we ship code? For engineering leaders, the paper argues, that is the wrong headline metric. The decisive question is Total Cost of Ownership (TCO) — and TCO is best understood by tracing how each workflow distributes its burden between Capital Expenditure (CapEx), the upfront investment to build something, and Operational Expenditure (OpEx), the ongoing cost to run, fix, and maintain it. The pivotal AI-era twist: OpEx is now heavily dictated by the token economy. Every interaction with an LLM is metered per token, so operational cost is no longer just engineer-hours — it is also a literal API bill that scales with how you feed and re-prompt the model.

The leadership reframe: from velocity to TCO

Velocity measures one moment — generation. TCO measures the whole lifecycle. Two workflows can look identical at the speed-of-first-draft level yet sit at opposite ends of the cost spectrum once you account for the months of running, debugging, and securing the code. The economic signature of a workflow is therefore the shape of its CapEx/OpEx split, not its day-one output rate.

The hidden debt of vibe coding: low CapEx, high OpEx

Vibe coding looks almost free. The barrier to entry is essentially zero — a monthly subscription to an AI assistant plus a few casual prompts. CapEx is negligible because the developer leans entirely on the model's baseline capability instead of investing time in system design.

That low entry cost masks a compounding OpEx burden along three axes:

  • Token burn rate. Developers dump massive, unstructured files into the context window and repeatedly ask the model to fix its own unverified mistakes. The result is an expensive "prompting loop" that burns API tokens with a low first-pass success rate — you pay, fail, re-prompt, and pay again.
  • Maintenance tax. Ad-hoc prompting produces code that lacks structural consistency. When a bug surfaces six months later, human engineers spend days reverse-engineering unstructured, AI-generated "spaghetti" before they can even begin the fix.
  • Security remediation. Without an automated evaluation harness, rapid code generation becomes rapid vulnerability generation. Fixing a security flaw in production is exponentially more expensive than catching it at the design phase.

The investment of agentic engineering: high CapEx, low OpEx

Agentic engineering flips the model. It demands a deliberate, upfront investment of engineering time before a single line of production code is generated: designing API schemas, building deterministic test suites, and — most importantly — structuring the agent's context.

That higher CapEx buys a dramatically lower marginal cost per feature. Because the AI operates inside a strictly governed "factory," its output is structurally sound, pre-tested, and aligned with company standards. The cost of shipping and maintaining each subsequent feature drops, and the expensive trial-and-error loops never get a chance to form.

Context engineering as a financial lever

In the token economy, context engineering is not merely a technical skill — it is a financial strategy. LLMs charge for every piece of information you send, so passing an entire 100,000-token repository into every prompt is financially unviable at scale.

Effective context engineering ensures the model receives a dense, high-signal payload — a precise AGENTS.md and architectural guardrails — rather than a sprawling, noisy one. Providing the right context upfront raises the agent's first-pass success rate, which is what eliminates the costly trial-and-error loops that plague vibe coding. To push OpEx lower still, advanced agentic engineering relies on dynamic context loaded on demand through skills and tool calling such as Model Context Protocol (MCP) servers — covered in depth in the Day-3 companion paper on Context Engineering. You pay the token cost only for the knowledge a task actually needs.

Intelligent model routing

A vibe coding workflow typically funnels every interaction through a single, massive frontier model — paying premium token prices just to ask the AI to fix a typo or generate a basic unit test.

A well-designed factory avoids that waste. It reserves large, advanced models for genuinely complex tasks — requirements, architecture, and initial implementation — and automatically routes deterministic, low-complexity tasks — test generation, code review, and CI/CD monitoring — to smaller, faster, and significantly cheaper models. By orchestrating a multi-model ecosystem, teams maintain peak output quality while systematically driving down the operational token cost.

  • Context engineering is a financial lever, not just a quality lever. Dense, high-signal payloads raise first-pass success, and first-pass success is what kills the expensive re-prompting loop.   • The flip is the whole point. Vibe coding trades near-zero CapEx for compounding OpEx — token burn, maintenance tax, security remediation. Where to Start and the Durable Principles

The shift from syntax to intent is not a future state; it is the work in front of us today. Whether you read this as an individual builder or as a leader thinking about how a team or an organization adopts these tools, one principle holds across every level: AI amplifies the engineering culture it lands in. A team with strong tests, clear architecture, and healthy review gets a force multiplier; a team without them gets its weaknesses multiplied just as fast. The checklists below translate that principle into action at three scales, and the section closes with the three principles the authors expect to outlast any specific tool.

For Individual Developers

  1. Set up an AGENTS.md (or equivalent). Pick the convention that matches your coding agent. Start with ten lines: stack, conventions, hard rules, workflow. Add a rule every time the agent does something it should not do again.
  2. Install a set of skills for your coding agents (such as Agents CLI) to build, evaluate, deploy, and optimize agents.
  3. Make one repetitive workflow your first agent. A research workflow, a code-review process, a recurring report. Prototype it with a coding agent and graduate it to production when it earns its keep. Building one agent end to end teaches more than reading about a hundred.
  4. Write the tests and evals before generating the code. Together they are the contract with the AI — they communicate intent more precisely than any prompt and turn vibe coding into agentic engineering.
  5. Review every line that ships. Be skeptical of anything that looks clever, check imports for real packages, and verify error handling covers realistic failure modes. Code the team does not understand becomes debugging cost it cannot afford.
  6. Maintain your own developer skills. Treat AI as a way to apply expertise at greater scale, not a substitute for it. Debugging, system design, and intuition for performance and correctness have to stay sharp.

For Engineering Leaders

  1. Make context engineering first-class. Treat AGENTS.md, system prompts, eval suites, and skill libraries as code: reviewed in PRs, versioned with the project, owned by named engineers. Otherwise the harness drifts and agent behavior becomes irreproducible across the team.
  2. Set the bar at the eval, not the demo. A demo proves an agent can succeed once; a passing eval suite proves it succeeds reliably. Define an explicit rubric — task success, tool-use quality, trajectory compliance, hallucination, response quality — and require eval coverage before any agent ships into a shared workflow, the way test coverage gates a service deployment.
  3. Re-shape code review for AI-generated code. It needs equal or greater scrutiny than human code, with extra attention to hallucinated dependencies, inadequate error handling, and subtle correctness gaps that look right at a glance. Train reviewers on those failure modes and tune checklists accordingly.
  4. Distinguish prototyping from production in team norms. Make the boundary explicit — which projects, branches, and environments warrant vibe coding versus agentic engineering. Teams that keep this blurry ship prototypes by accident.
  5. Invest in harness components as a shared team asset. Reusable prompts, skill libraries, MCP connections, and eval harnesses compound across projects. Build the harness once and refine it many times.

For Organizations

  1. Treat AI-assisted development as an engineering investment, not a productivity feature. The largest gains come from pairing AI tooling with eval coverage, observability, and architectural standards. Rolling out an agent without that scaffolding produces speed without quality — and technical debt faster than any team can repay.
  2. Invest in the production substrate before scale. A vibe-coded prototype is not a production system. What graduates it is operational discipline: trajectory and final-response evals in CI, traces of every agent run, scoped permissions per agent, and security review tuned to generated-code failure modes. Build this before the first production agent ships.
  3. Adopt open standards. MCP for tool access and A2A for cross-agent delegation are converging into the connective tissue of multi-agent systems. Choosing them now keeps the option to mix vendors and frameworks open and avoids re-platforming later.
  4. Plan for hybrid human-plus-agent teams. The strongest results come from architectures where humans set direction, agents implement, and clear handoff protocols govern the boundary. Code review, on-call rotations, and team structures all evolve to reflect that agents are now participants, not just tools.
  5. Reframe hiring around judgment, not implementation. As implementation gets faster, the bottleneck shifts to specification, evaluation, architectural judgment, and review. The most valuable engineers will be the ones who direct agents well, not the ones who write the most code.

The Three Durable Principles

Principle What it means Practical implication
Structure scales, vibes don't Vibe coding is valid for exploration and personal projects, but software organizations depend on requires specs, tests, guardrails, and human oversight of architecture. Gate production work behind agentic-engineering discipline; the gap between "it seems to work" and "it works correctly under all conditions" is where outages and vulnerabilities live.
AI amplifies your engineering culture AI is a force multiplier of both strengths and weaknesses; strong testing, clear standards, and healthy review compound, while their absence compounds too. Fix the culture and the harness first; tooling alone will not rescue a team without discipline.

Invest in judgment-centric skills and roles; the builders who direct agents well become more valuable, not less.
