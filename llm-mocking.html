LLM Mocking for Flow Tests

The whole story in two tabs: what we need from a mock strategy for tests/flows/, and which tools can deliver it. Start with Requirements — it sets the key needs the Options tab is scored against.

Scope: tests/flows/ Stacks: litellm + LangGraph create_agent Deeper background: old_LLM_MOCKING_OPTIONS.html
Read this first · the key need

What we're looking for

We need reliable LLM mocking for the flow tests in tests/flows/ that replaces what we have today — chiefly FakeAgentGraph in the chat_agent_flow suite. "Reliable" means: deterministic and offline, but running enough of the real agent so a green test actually means the flow works. The motivation below explains why the current stub falls short; the numbered requirements are the bar any replacement must clear.

What FakeAgentGraph is

In production the chat flow runs langchain.agents.create_agent(...) — a LangGraph ReAct agent: the LLM decides which tool to call, the graph executes it, feeds the result back, the LLM decides the next step, and a chain of ~9 middlewares wraps the whole loop. FakeAgentGraph (tests/flows/chat_agent_flow/fake_agent_graph.py) replaces that entire graph with a stub that takes an author-scripted list of tool calls and awaits each tool's raw .coroutine in order.

Why that's a problem — what it silently stubs out

  • It fakes the agent's whole reason to exist. An agent's job is to decide and sequence tool calls across turns. The fake hardcodes that sequence, so the orchestration — the actual product behavior — is never exercised.
  • It drops all ~9 middlewares (analytics, call-count limits, max-LLM-call guard, structured-response, prompt-caching, model retry/fallback), keeping only mw.tools. Those are our code and run for real users; the tests cover none of their behavior.
  • It skips pydantic arg-validation. await tool.coroutine(**args) bypasses BaseTool.ainvoke/_parse_input, so scripted tool args that the real arg-schema would reject still "pass."
  • No multi-turn feedback. Real tool results become ToolMessages fed back into the next model decision; the fake just runs a flat list.
  • Silent failure modes: filesystem tools are silently skipped; unknown tool names KeyError — green-but-empty risk.

The goal

Run the real create_agent with a mocked model instead of a faked graph — recovering the real ReAct loop, middleware chain, ToolMessage feedback, and arg-validation, while still feeding the test author's canned model output.

Note on scope: no mock makes the tool-call decision realistic — the author always scripts which tool/args the model "chooses." Replacing the fake buys realistic plumbing (the loop, middleware, validation), not realistic decisions. Fuller background lives in old_LLM_MOCKING_OPTIONS.html.

Requirements

A candidate mock mechanism (see the Tool Options tab) is scored against all of the following.

1
Allow canned answers from tests

The test author can supply the model's output (text, tool calls, structured output) directly from the test, deterministically.

2
Popular

An actively maintained, widely-adopted tool — not a bus-factor-1, sub-1-year-old project we'd be betting a multi-year suite on.

3
Allow returning errors and timeouts

Tests can inject failure modes — provider errors, timeouts — to exercise the retry/fallback paths.

4
Works with LangGraph and LiteLLM

One mechanism covers both stacks: the LangGraph create_agent agent flow and the litellm path.

5
Allow checking whether the LLM was called

Tests can assert that the model was (or wasn't) invoked — and how often — to verify the flow actually reached the LLM.

6
Black-box as possible

Mock as few as possible of our own code — ideally zero. The mock should sit at the network layer, so the real provider SDK, the agent graph, middleware, and parsing all run for real and only the wire response is canned.

7
Python-friendly if not generic-endpoint based

If the tool doesn't expose generic endpoints (e.g. HTTP), it must be supported in Python and easy to wrap in a Pytest fixture.

8
Support all key LLM vendors

Covers the providers we actually use — OpenAI, Anthropic, Bedrock, Vertex — not just one or two.

In-process · the lead pair

respx — HTTP-layer mock · primary recommendation

Popular: 812★, the de-facto httpx mocking lib.  Maintained: yes v0.23.1, Apr 2026 (repo currently pins 0.21.1).

★ / dl: 812★ · 17.6M/mo  ·  Testing tool: yes  ·  Canned answers: yes (routes → Response)  ·  LangGraph: ◐ indirect — intercepts the httpx wire langchain rides; no direct mention

Patches httpx's sync+async transport with a mock router: you register routes (matched on method / URL / headers / body) that return canned httpx.Response objects, including streamed SSE byte chunks. Because it intercepts at the transport boundary, everything above the wire runs for real — the provider SDK, and on Stack B the real bind_tools, with_structured_output parsing, retry and fallbacks. One mechanism covers both stacks (litellm and langchain-anthropic/openai both use httpx). Blind spot: Bedrock rides botocore, not httpx, so respx can't see it.

In a tests/flows/ test
import httpx, respx

@respx.mock
async def test_when_user_replies_then_agent_posts_inline_reply(github_mock):
    # Arrange — canned answer at the Anthropic wire; everything above runs for real
    route = respx.post("https://api.anthropic.com/v1/messages").mock(
        return_value=httpx.Response(200, json={
            "role": "assistant", "stop_reason": "end_turn",
            "content": [{"type": "text",
                         "text": "Because the query concatenates user_id directly."}],
        }))

    # Act — real create_agent + 9 middlewares + ToolMessage feedback all execute
    response = await call_incoming_pr_webhook(
        make_review_comment_webhook(body="why is this flagged?"),
        event="pull_request_review_comment")

    # Assert
    assert response.status_code == 202
    assert route.called  # req. 5: the model was actually reached
    github_mock.reply_to_review_comment_from_comment_id.assert_called_once()

pytest-httpx — httpx mock, as a fixture

Popular: 454★ — smaller following than respx, standard in the pytest+httpx crowd.  Maintained: yes v0.36.2, Apr 2026.

★ / dl: 454★ · 10.1M/mo  ·  Testing tool: yes (pytest fixture)  ·  Canned answers: yes  ·  LangGraph: ◐ indirect — same httpx transport as respx

Same interception point as respx (httpx transport), exposed as a pytest fixture (httpx_mock) rather than a decorator/context-manager router; it also asserts every registered response was consumed. Functionally interchangeable with respx for our purpose — the choice is ergonomics (fixture style vs. router style), not capability. Identical Bedrock blind spot.

In a tests/flows/ test
async def test_when_user_replies_then_agent_posts_inline_reply(github_mock, httpx_mock):
    # Arrange — registered as a fixture; auto-asserts the response was consumed
    httpx_mock.add_response(
        url="https://api.anthropic.com/v1/messages",
        json={"role": "assistant", "stop_reason": "end_turn",
              "content": [{"type": "text",
                           "text": "Because the query concatenates user_id directly."}]})

    # Act
    response = await call_incoming_pr_webhook(
        make_review_comment_webhook(body="why is this flagged?"),
        event="pull_request_review_comment")

    # Assert
    assert response.status_code == 202
    assert httpx_mock.get_request() is not None  # req. 5: model was reached
    github_mock.reply_to_review_comment_from_comment_id.assert_called_once()

litellm built-in mock_response

Popular: ships inside litellm (52k★; 1.83.1 installed).  Maintained: yes — first-party, actively released.

★ / dl: 52k★ · 497M/mo (whole lib)  ·  Testing tool: yes (built-in test hook)  ·  Canned answers: yes (streaming ✓; tool-calls hand-built)  ·  LangGraph: n/a — Stack A only

litellm has first-class test hooks: pass mock_response="…" (or a dict for tool calls) to acompletion and it short-circuits before httpx, returning a synthetic ModelResponse. Zero infra, perfectly deterministic. But it only covers Stack A — the agent flow's langchain-anthropic path never goes through litellm, so this does nothing for it. Tool-call mocking means hand-building the response dict (no public mock_tool_calls helper).

In a tests/flows/ test (Stack A — the litellm path)
# Today the `llm` fixture hand-fakes acompletion's return value. The litellm-native
# variant lets litellm build the synthetic ModelResponse from mock_response instead,
# so the real response parsing runs. Inject it on the handler seam:

@pytest_asyncio.fixture
async def litellm_canned():
    canned = {"text": "did_suggestion_impact_commit: true"}
    real = litellm.acompletion

    async def _with_mock(*args, **kwargs):
        return await real(*args, mock_response=canned["text"], **kwargs)

    with patch("pr_agent.algo.ai_handlers.litellm_ai_handler.acompletion", _with_mock):
        yield canned  # a test can reset canned["text"] per scenario

async def test_when_commit_fixes_finding_then_comment_is_marked_resolved(github_mock, litellm_canned):
    litellm_canned["text"] = "did_suggestion_impact_commit: true"
    response = await call_incoming_pr_webhook(make_push_webhook())
    assert response.status_code == 202
    github_mock.aresolve_review_thread.assert_called_once()
    # errors/timeouts (req. 3): set mock_response=litellm.Timeout(...) to raise instead
Agent flow · the harness for Stack B

LangGraph FakeToolCallingModel (vendored) + real create_agent

Popular: n/a — not a package; a ~40-line class that lives only in langgraph's own test suite (not a public export).  Maintained: you own it once vendored — upstream may drift.

★ / dl: n/a (not a package)  ·  Testing tool: yes  ·  Canned answers: yes (scripted AIMessages)  ·  LangGraph: ✅✅ it IS langgraph's own test fixture

This is the only thing that makes "scripted model into the real graph" work. The class is a BaseChatModel that implements bind_tools (records the bound tools) and returns pre-scripted AIMessages carrying tool_calls — those scripts are your canned answers. Inject it as the model into the real create_agent, and the real ReAct loop, your ~9 middlewares, ToolMessage feedback, and BaseTool.ainvoke pydantic arg-validation all execute; only the model's "decision" is hand-written. Gap: it does not implement with_structured_output, so the structured-response path stays stubbed (that's respx's job). Needed because the stock langchain-core fakes (below) can't bind tools.

In a tests/flows/ test (Stack B — replaces FakeAgentGraph)
from langchain.agents import create_agent
from langchain_core.messages import AIMessage
from tests.flows.chat_agent_flow.fakes import FakeToolCallingModel  # vendored ~40-line class

async def test_when_user_asks_to_dismiss_then_agent_dismisses_then_replies(github_mock):
    # Arrange — the script IS the canned answer: turn 1 calls a tool, turn 2 replies
    model = FakeToolCallingModel(tool_calls=[
        [{"name": "dismiss_finding", "args": {"finding_id": "42"}, "id": "c1"}],
        [],  # no tool call -> the loop ends
    ], responses=[AIMessage("Dismissed — thanks for flagging.")])

    # the real graph runs; only the model object is faked
    def _real_graph_fake_model(**kw):
        return create_agent(**{**kw, "model": model})

    # Act — real ReAct loop, 9 middlewares, ToolMessage feedback, pydantic arg-validation
    with patch("pr_agent.algo.agents.chat_agent.create_agent", _real_graph_fake_model):
        response = await call_incoming_pr_webhook(
            make_review_comment_webhook(body="please dismiss this"),
            event="pull_request_review_comment")

    # Assert
    assert response.status_code == 202
    github_mock.aresolve_review_thread.assert_called_once()  # the real tool fired
    assert model.invoke_count == 2  # req. 5: model reached twice (the ReAct turns)
Cross-process · if you want one mechanism for everything incl. Bedrock+Vertex

CopilotKit aimock — multi-provider mock server · formerly llmock

Popular: 637★, vendor-backed, fast-growing.  Maintained: very active — v1.35.0, Jun 28 2026 (the llmock repo 301-redirects here; same product renamed).

★ / dl: 637★ (npm pkg)  ·  Testing tool: yes  ·  Canned answers: yes (fixtures / record-replay)  ·  LangGraph: ✅ site lists LangGraph explicitly; has a langchain integration guide

A standalone (TypeScript/Node) HTTP server you run on one port and point your SDK base-URLs at; it speaks ~14 provider wire formats (OpenAI/Claude/Gemini/Azure/Bedrock/Vertex), full SSE streaming, multi-round tool calls with result matching, record/replay fixtures, and fault injection. From Python you launch it as a subprocess. Its one real edge over respx is being the only verified single mechanism that also covers Bedrock + Vertex; its cost is a CI process to manage (port/startup races — the exact flakiness this migration is trying to kill) and its youth.

In a tests/flows/ test (cross-process server)
import subprocess, pytest_asyncio

@pytest_asyncio.fixture
async def aimock_server():
    proc = subprocess.Popen(["npx", "aimock", "--port", "8731",
                             "--fixtures", "tests/flows/fixtures/chat_replies.json"])
    await wait_for_port(8731)          # the port/startup race to manage in CI
    yield "http://localhost:8731"
    proc.terminate()

async def test_when_user_replies_then_agent_posts_inline_reply(github_mock, aimock_server, monkeypatch):
    # Arrange — point the SDK base-URL at the mock server (covers Bedrock/Vertex too)
    monkeypatch.setenv("ANTHROPIC_BASE_URL", aimock_server)

    # Act — real SDK + real graph run their wire path against the server
    response = await call_incoming_pr_webhook(
        make_review_comment_webhook(body="why is this flagged?"),
        event="pull_request_review_comment")

    # Assert
    assert response.status_code == 202
    github_mock.reply_to_review_comment_from_comment_id.assert_called_once()

vcr.py + pytest-recording — record/replay cassettes

Popular: vcr.py 3.0k★ (the canonical Python cassette tool).  Maintained: yes — vcr.py 8.2.1 Jun 2026; pytest-recording (610★) is the pytest wrapper (@pytest.mark.vcr), though its last release was v0.13.4 May 2025.

★ / dl: vcr.py 3.0k★ · 15.8M/mo; pytest-recording 610★  ·  Testing tool: yes  ·  Canned answers: ◐ recorded cassettes, not hand-scripted  ·  LangGraph: ◐ indirect — captures the httpx layer; no langgraph-specific support

Records real HTTP interactions to YAML "cassettes" on first run, then replays them offline forever after — maximally faithful because the bytes are genuine provider responses. Best reserved for a small set of high-fidelity contract tests, not a default: cassettes drift, bloat, and need re-recording against a live key. (The langchain-specific vcr-langchain wrapper is dead — use vanilla vcr.py.)

In a tests/flows/ test (record once, replay forever)
import pytest

@pytest.mark.vcr  # 1st run with a live key records cassettes/test_..._reply.yaml; then offline
async def test_when_user_replies_then_agent_posts_inline_reply(github_mock):
    # Act — genuine provider bytes replay from the cassette; real graph + parsers run
    response = await call_incoming_pr_webhook(
        make_review_comment_webhook(body="why is this flagged?"),
        event="pull_request_review_comment")

    # Assert
    assert response.status_code == 202
    github_mock.reply_to_review_comment_from_comment_id.assert_called_once()
    # canned answers (req. 1) are recorded, not hand-scripted; to inject an error,
    # hand-edit the cassette YAML to a 500 / timeout body
Context · why you can't just use the shipped fakes

langchain-core stock fake chat models

Popular: ship with langchain-core (very widely used).  Maintained: yes, but insufficient here.

★ / dl: bundled in langchain-core  ·  Testing tool: yes  ·  Canned answers: yes (scripted strings)  ·  LangGraph: ◐ same ecosystem, but bind_tools/with_structured_output raise NotImplementedError — can't drive a tool agent

GenericFakeChatModel, FakeMessagesListChatModel, ParrotFakeChatModel replay scripted strings as a BaseChatModel — fine for plain prompt→text tests. But they inherit BaseChatModel.bind_tools and .with_structured_output, both of which raise NotImplementedError (confirmed live on installed 1.2.27). So they cannot drive a tool-binding agent — which is precisely why the agent harness has to vendor FakeToolCallingModel instead.

Why it doesn't work for our agent flow
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage

model = GenericFakeChatModel(messages=iter([AIMessage("plain text reply")]))
# Fine for a prompt -> text flow test:
#   reply = await model.ainvoke("hello")   # -> "plain text reply"

# But the chat agent binds tools, and that is exactly what raises:
model.bind_tools([dismiss_finding_tool])   # NotImplementedError
model.with_structured_output(ChatAgentResponse)   # NotImplementedError
# -> can't drive create_agent; use the vendored FakeToolCallingModel above.

Ruled out — and why (so nobody re-discovers them)

  • moto (8.6k★) — bedrock-runtime only stubs invoke_model (1 of 10 ops); converse and the other 8 are unimplemented and raise. Dead end for converse-based LLM calls.
  • LocalStack Pro Bedrock — emulates by running a real local model (Ollama); paid + non-deterministic output. Wrong tool when you want canned answers.
  • vcr-langchain — dead (last push Jun 2024, pins ancient LangChain). Superseded by vanilla vcr.py.
  • mock-ai (ajac-zero) — ~14★, OpenAI+Anthropic only, bus-factor 1. Too immature for a foundation.
  • ai-mocks (mokksy) — Kotlin/JVM, not Python.
  • openai-responses-python — OpenAI Responses API only, maintenance mode (v0.13.1 Dec 2025). Our stack is litellm + langchain-anthropic.
  • LangSmith pytest + langsmith[vcr] — cloud-coupled (account/network); only the VCR cache is offline. Heavyweight for this.
The finding that shapes the ranking: there is no official public "agent test harness" for create_agent that runs the real graph with a scripted model — the closest supported path is vendoring FakeToolCallingModel. Combined with the with_structured_output gap, that's why respx (which runs the real binding) leads, with the fake-model harness as the complement for tool-trajectory and middleware coverage.

Net read, per option

  • FakeAgentGraph current — What we're replacing. Replaces the whole graph, so middleware never runs, tools are awaited raw (no arg-validation, filesystem tools silently skipped), with_structured_output is hand-built, and the tool sequence is a flat script, not a real ReAct loop. Cheap and deterministic, but a green test proves little about the real flow.
  • AsyncMock on acompletion current — The litellm path today (the llm fixture). Patches our handler function above the wire, so it's not black-box, but for the non-agent litellm path that's fine: native call-assertions, trivial error injection, zero infra. No agent graph in this path, so the fidelity columns don't apply.
  • respx — Primary pick. Wire-level, runs the real binding for both httpx stacks; blind to Bedrock (botocore).
  • pytest-httpx — Same wire interception as respx, exposed as a fixture. The choice is ergonomics, not capability.
  • litellm mock_response — LiteLLM path only — the langchain agent path never goes through litellm. Zero-infra and native for the litellm path.
  • FakeToolCallingModel + real create_agent — The LangGraph harness. Runs the real graph + 9 middlewares; mocks our model object, not the wire. Vendored, not a package.
  • CopilotKit aimock — The only single mechanism that also covers Bedrock + Vertex. Cost: a CI subprocess (port/startup races) and its youth.
  • vcr.py + pytest-recording — Highest fidelity (genuine bytes), but recorded not scripted; cassettes drift. Best for a few contract tests.
  • langchain-core stock fakes — Context only: bind_tools/with_structured_output raise, so they can't drive a tool agent. This is why FakeToolCallingModel is vendored.
How to read the table: no single row is all-✓✓. The shape of the recommendation is a pair — respx (or pytest-httpx) for wire-level fidelity on the httpx stacks, complemented by the FakeToolCallingModel harness for the real graph + middleware coverage that the wire mocks can't script. Reach for aimock only if covering Bedrock + Vertex through one mechanism outweighs running a CI subprocess.
