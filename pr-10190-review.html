Domain primer · for someone new to this

What is "Vortex"?

Slice is an equity / cap-table platform. Many actions have a ripple effect: e.g. editing a vesting schedule (the rules for how equity is earned over time) means every grant, share, and warrant that uses that schedule must be recalculated. Today, one API call does the edit and re-runs all that dependent work inline, synchronously, in a single request.

Vortex is Slice's in-house orchestration layer built on Temporal. It turns that one big synchronous call into a DAG (a directed graph of steps): a "parent node" does the core edit, and "child nodes" fan out — one per affected domain — to redo their piece, in parallel, each retryable on its own. The payoff is durability (a crash mid-way can resume), independent retries, batching over large sets, and per-step progress shown in the UI.

Concretely, each node is just a controller method tagged with a decorator (@VortexParent / @VortexChild). A build script (scripts/generate-topology.ts) scans those decorators and produces the graph that a worker service (vortex-brain) executes. This PR's recipe uses the real vesting-schedule → grants/shares/warrants conversion (which already exists in the codebase) as its worked example. I verified those controllers, decorators, and the topology script all exist on main.

What is the "date / timezone" problem?

Two kinds of dates behave very differently, and mixing them up is a classic source of "off-by-one-day" bugs:

  • Calendar-day values (a grant date, a vesting date, a 409A valuation date) mean "this exact day, everywhere." 2024-01-01 must stay Jan 1 for a user in Tokyo and in Los Angeles alike.
  • Instants (createdAt, an event timestamp) mean "this exact moment," and should be shown converted into each viewer's local timezone.

The bug the docs guard against: JavaScript's new Date('2024-01-01') is UTC midnight, but dayjs(value) parses in the browser's local zone — so in a positive-offset zone (e.g. Israel, UTC+2/3) a bare YYYY-MM-DD silently rolls back to the previous day. The two new reference docs give a concrete "shift audit" (Construct → Parse/Pick → Anchor/Transport → Round-trip → Display) and point at the project's real helpers (getStartOfDateUTC, ParseUTCIsoDatePipe, the UTC-default SliceDatePicker, formatDateInUtcTimezone) so agents stop reintroducing the shift. I confirmed all of those symbols exist.

Design idea · reviewer's proposal

Put the workflow in one file; hang knowledge and sub-agents off each step

The conversion workflow is currently authored twice. convert-vortex.md defines a 6-step sequence and conversion-recipe.md defines an overlapping 8-step sequence plus the audit, so the command and the recipe are both steering the same ordered process, each holding part of it. "Decide the node graph first", "regenerate topology", and "run the audit" all appear in both, and the command's step 5 ("apply the recipe steps in order") exists only to defer to the other file. The result is that there is no single source of truth for what the steps are or when the gates fire: changing the process means editing two files in sync, and drift between them is the natural failure mode. It also conflates two different kinds of content — orchestration (the ordered steps and their pass/fail gates) and knowledge (how to actually write a parent controller, a batched child, the DTOs).

The cleaner shape is to keep the workflow in exactly one file: the canonical ordered steps, with every validation and audit check inlined as a gate the run must pass. Everything else becomes leaf content the workflow pulls in on demand — one knowledge doc per step (or topic) for the "how", and, for the heavier or independently verifiable steps, a sub-agent that owns that step end-to-end and reports its outcome back. The command collapses to a thin entry point (identify the target flow, then run the workflow), SKILL.md stays as routing and positioning, the recipe's step bodies move into the per-step knowledge docs, and the audit becomes the workflow's closing gate — ideally enforced by a reviewer sub-agent. You get one place to read and change the process, single-source-of-truth restored, and, as a bonus, exactly the structure that closes the workflow-instrumentation gaps flagged earlier: tracked steps, per-step artifacts, and a reviewer in the loop.
