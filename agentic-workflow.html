What is the orchestrator?

The orchestrator is whatever drives the pipeline end-to-end. It carries the workflow's shape — when to plan, when to implement, when to verify — and it's where you bake in your team's defaults. Bigger orchestrators (SDD frameworks) impose more structure; lighter ones (a custom slash command) leave more freedom but require more discipline.

Option A

Custom slash command

A one-file prompt that scripts the phases via a single command.

  • Lowest setup cost — a markdown file
  • Easy to evolve and re-share across repos
  • No built-in state — restart loses context
  • You write the verification logic yourself
Best for: small teams, prototypes, opinionated solo workflows.
Option B

Orchestrating skill

A reusable skill that wraps subagents, scripts, and prompts into one entry point.

  • Composes with other skills cleanly
  • Can ship with helper scripts & templates
  • Heavier than a command — needs structure
  • Discoverability depends on description quality
Best for: teams already invested in the skills ecosystem.
Option C
Recommended

SDD framework

A spec-driven framework like OpenSpec or Superpowers — the workflow lives inside the framework's own commands.

  • Plan, design, tasks, verification — all native
  • Living spec layer survives across sessions
  • Battle-tested patterns (TDD, micro-tasks, deltas)
  • Stronger opinions — less room to deviate
Best for: teams that want structure baked in, especially on brownfield repos.
Other

Your option here

Leave room for in-house orchestrators, n8n pipelines, or hybrid approaches that mix a skill with a command and an SDD checkpoint.

What is planning & design?

Take the architecture document and turn it into a reviewable plan — concrete enough that an agent can execute it without re-deciding scope at every step. If you bake your workflow into an SDD framework, the planning phase usually rides along with the orchestrator.

Option A
Recommended

OpenSpec proposals

Each change gets a folder with proposal, specs, design, and tasks.

  • Living spec layer — survives the conversation
  • Delta specs handle brownfield projects well
  • Requires adopting the OpenSpec lifecycle
Workflow: /opsx:propose → /opsx:apply → /opsx:archive
Option B

Superpowers brainstorm & plan

Socratic brainstorm, then a plan of 2–5 minute micro-tasks with explicit verification steps.

  • Micro-tasks → easy to dispatch to subagents
  • TDD enforced at the task level (RED-GREEN-REFACTOR)
  • More ceremony — overkill for trivial changes
Best for: non-trivial features where rigor outweighs speed.
Option C

Copilot plan mode

Copilot's built-in planning tools that coordinate multi-step execution natively in the IDE.

  • Zero setup — lives in Visual Studio / VS Code
  • Tight coupling with Copilot agent mode
  • Less portable — plans live in the IDE session
  • Lighter than SDD on spec discipline
Best for: teams already standardized on Copilot end-to-end.
Other

Your option here

RFC docs in Notion, Linear specs, Kiro, GitHub Spec Kit, in-house templates — leave room for anything that produces an agent-executable plan.

What does implementation mean here?

The agent picks up tasks from the plan and produces code. We standardize on GitHub Copilot agent mode as the base technology — it's GA across VS Code and JetBrains, autonomously edits files and runs commands, and integrates cleanly with both custom instructions and any planning layer sitting above it.

Base
Standard

Copilot agent mode

Autonomous, synchronous collaborator that edits files across the repo and runs commands until the task is complete.

  • GA on VS Code & JetBrains (as of Mar 2026)
  • Reads copilot-instructions.md for guardrails
  • Integrates with planning + custom prompts
  • Premium request usage — watch the budget
Variant

Copilot CLI / cloud agent

Same agent, different surface — terminal or PR-driven background execution.

  • Async runs — file an issue, get a PR
  • CLI is great for scripted orchestration
  • Less interactive — harder mid-task steering
Variant

Subagent-driven execution

If you're on Superpowers, each task in the plan is dispatched to a fresh subagent with a two-stage review.

  • Cleaner context per task
  • Built-in spec + code-quality review gates
  • Adds latency vs. monolithic agent runs
Other

Your option here

Claude Code, Cursor, Cline, Windsurf, in-house agents — the loop shape doesn't change, only the executor does.

What is the verification phase?

Verification is the agent's contract with the codebase: a change isn't done until it compiles, lints clean, and the test suite is green. The loop arrow exists because verification routinely sends the agent back to fix things.

Gate 1

Compilation

Fastest signal — does the project still build?

  • Sub-second feedback in most stacks
  • Catches whole categories of bad edits cheaply
  • Dynamic languages get little value here
Gate 2

Linting

Style + correctness rules the agent didn't internalize from instructions.

  • Cheap to run, runs locally and in CI
  • Encodes team conventions explicitly
  • Noisy if the ruleset isn't well-tuned
Gate 3
Required

Test suite

The behavioral contract — most agentic workflows treat a green suite as the definition of done.

  • Catches semantic regressions linting misses
  • Pairs naturally with TDD-style planning
  • Slow suites become a bottleneck — invest in speed
Other

Your option here

Type checks, security scanners, contract tests, screenshot diffs, smoke runs in a sandbox — add gates that match the risk profile of the change.

What are coding practices?

The standards, patterns, and guardrails the agent applies while writing code — naming, error handling, layering, test style. This is a side asset to the implementation phase: it doesn't drive the workflow but it shapes every line of code the agent produces.

Option A
Recommended with Copilot

Copilot custom instructions

A .github/copilot-instructions.md file plus path-scoped *.instructions.md rules with applyTo globs.

  • Always-on across chat, agent mode, CLI, PR review
  • Path-scoped rules target specific folders/files
  • Repo-versioned — travels with the code
  • Doesn't affect inline ghost-text completions
Tip: keep each rule short and self-contained — one statement per line.
Option B

Coding-practices skill

A reusable skill the orchestrator invokes when implementation begins. The skill carries practices, examples, and lint config.

  • Portable across repos and agents
  • Can bundle scripts, templates, and references
  • Easier to evolve in isolation
  • Requires a skill-aware orchestrator to fire
Best for: consultancy patterns reused across multiple client repos.
Option C

AGENTS.md / framework conventions

Use the conventions your SDD framework already reads (e.g. AGENTS.md, framework-specific docs folders).

  • Zero extra config when you've already adopted SDD
  • Same file picked up by multiple agents
  • Lower priority than Copilot's own instruction layers
Other

Your option here

Cursor rules, MCP-served knowledge bases, in-house lint plugins, ADRs surfaced via tool — any mechanism that ships standards into the agent's context.

What is the summary phase?

Once verification is green, the agent closes the loop: a concise account of what changed, why, what was tested, and what still needs human attention. This is what gets reviewed, archived, and surfaced in the PR description.

Option A
Recommended

Structured PR description

A templated summary: what changed, decisions taken, gates passed, open follow-ups.

  • Lives where reviewers already look
  • Drives Copilot code review with context
  • Easy to drift if not enforced by the orchestrator
Option B

OpenSpec archive

The change folder closes via /opsx:archive, merging deltas back into the living spec.

  • Spec stays in sync with reality automatically
  • Auditable trail of every change
  • Requires the OpenSpec orchestrator path
Option C

Conversational handoff

Lighter touch — a structured chat reply with bullet points, ready to paste into Slack or Linear.

  • Fast — no extra tooling
  • Good for exploratory work
  • No durable artifact unless you save it
Other

Your option here

Changelog entries, ADR updates, release notes drafts, observability annotations — extend the summary phase to whatever your team consumes downstream.

A note on the base

Copilot is the base. The shape is the workflow.

We standardize on GitHub Copilot agent mode as the executor. Everything above it — the orchestrator, the planning layer, the coding practices, the verification gates — is the part we choose deliberately. Swap the base later and the diagram still holds.
